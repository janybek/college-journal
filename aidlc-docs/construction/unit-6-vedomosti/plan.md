# Юнит 6 «Ведомости, объявления, заявки»: план сборки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** последний юнит версии 1. Преподаватель, деканат и проректор открывают **ведомость предмета** (по юнитам ТК 40 + СРС 20 + рубежный 40, итог — среднее за юниты, оценка словом, ниже минимума — подсвечено), печатают её на A4 и выгружают в Excel. Преподаватель (и деканат) **закрывает юнит**, а на зачётной неделе — **итоговую ведомость**; после закрытия числа юнита меняются только **заявкой** «было / стало / причина» → деканат → проректор → журнал сам вносит правку и пишет «Журнал изменений». Деканат задаёт **зачётную неделю** (обычные пары на неё не ставятся) и ведёт **ведомость гос. экзамена** группы. Деканат, администратор и преподаватель пишут **объявления**; студент видит их на главной, а в «Оценках» — закрытые юниты, итог и свой гос. экзамен.

**Architecture:** числа ведомости не считаются заново — это ответ журнала (`journalView`, `studentResults` юнитов 3 и 5), переложенный в строки ведомости. Закрытие — строка таблицы «Закрытые юниты» (предмет + семестр по плану + юнит; юнит 0 — итоговая ведомость); числа при закрытии **не замораживаются**: закрытый юнит защищён тем, что все пути записи, которые меняют его числа, отвечают `unit_closed`. Заявка — строка таблицы «Заявки»; «было» сверяется с базой при подаче и при каждом согласовании; последнее согласование применяет правку тем же запросом (на SQLite — одна транзакция). Зачётная неделя — две строки «Настроек», которые исключают дни из расчёта рабочих дней. Гос. экзамен и объявления — свои таблицы и свои обработчики. Печать — печать браузера (print CSS, A4), Excel — уже лежащая в `site/vendor/` библиотека. Новых файлов на диске юнит не создаёт: ящик файлов, уборка и копии не меняются.

**Tech Stack:** как в юнитах 3–5 — Node 24, ES-модули, `node --test`, встроенный `node:sqlite`, esbuild только для запасной сборки Apps Script, сайт без сборки. Новых зависимостей нет.

**Spec:** `aidlc-docs/inception/design-v1.md` («Ведомость (вариант А)», «Закрытие юнита», «Заявки на исправление»), таблица решений `aidlc-docs/aidlc-state.md` — **24.11.2026 «Юнит 6 — вопросы до плана»**, 22.11 «Порядок юнитов меняется», 22.11 «План юнита 3», открытый вопрос «Система оценивания» (схема баллов не меняется до документа оценивания); планы юнитов 3 и 5 (модель журнала, СРС по заданиям, «Журнал изменений» — действуют без изменений, кроме прямо названного здесь). Где `design-v1.md` расходится с таблицей решений или этим планом, действуют они.

**Исходное состояние:** `HEAD 9a48bd8` (после `caf33d8` только документы), **923 теста** (`npm test` 24.11.2026). `npm run build:gas` при написании плана не запускался (он пишет в `build/`); на `caf33d8` собирался — сверка плана запускает заново. ## Global Constraints

Действующие правила юнитов 2–5 (переносятся без изменений):

- `core/` и `backend/` без зависимостей из npm. Dev-зависимости проекта: `esbuild`, `xlsx`, `@fontsource-variable/inter`. Новые не добавляются.
- Сайт: без сборки, без фреймворков, ничего не загружает с чужих адресов (ни CDN, ни внешних шрифтов).
- Все обработчики сервера синхронные. `handleRequest` никогда не бросает исключение и всегда возвращает объект ответа. Ошибки — `AppError(code, { fields })` из `core/errors.js`.
- Запрос сайта: `POST`, `Content-Type: text/plain;charset=utf-8`, тело — JSON `{action, token, data}`. Своих заголовков нет. (Исключение юнита 5 — `work.upload` через `XMLHttpRequest` — юнит 6 не трогает.)
- `passwordHash` никогда не попадает в ответ сервера. Ответы собираются по полям; строки сотрудников и студентов в ответ целиком не копируются.
- Время берётся только из `platform.now()`. `Date.now()` и `new Date()` без аргумента в `core/` и `backend/` запрещены. «Сегодня» — `localDate(platform.now())` по Бишкеку (UTC+6 круглый год). Сайт часам устройства не доверяет: «сегодня» он берёт из ответа сервера.
- Дата — строка `'YYYY-MM-DD'`, время — `'HH:MM'`, дата со временем — `'YYYY-MM-DD HH:MM:SS'` (`localDateTime`). Объектов `Date` в строках хранилища нет.
- В базе хранятся английские коды (`prorector`, `applied`, `teachers`), на экране они переводятся словарём.
- Обработчик читает каждую таблицу не больше одного раза за запрос (`store.list`) и пишет пачкой (`insertMany`, `updateMany`, `removeMany`). `store.get`, `store.update`, `store.remove` в цикле запрещены.
- Что попадает в сборку Apps Script, остаётся чистым: `backend/api.js`, `backend/handlers/*`, `backend/*.js` (кроме `backend/node/` и `backend/store/sqliteStore.js`), `core/*` не импортируют ничего из `backend/node/`; в них нет `node:`, `require(`, `Buffer` и слова `process` даже в комментариях (их ищет `tests/gasBundle.test.js`).
- Роли: `admin`, `dean`, `prorector`, `teacher`, `student`. У сотрудника роли хранятся строкой через запятую; у одного человека может быть несколько ролей (`dean,teacher`). Сервер смотрит на **все** роли человека; «в какой роли я сейчас» — только вид меню на сайте.
- Любая фраза на экране идёт через ключ словаря. Наборы ключей в `ky`, `ru`, `en` одинаковые (`tests/i18n.test.js`). Названия дней и месяцев — из словаря, без `Intl`.
- Данные с сервера, от пользователя и из файлов попадают на страницу только как текст (`textContent`, помощники из `site/js/ui.js`), никогда через `innerHTML`. Это относится к тексту объявления, причине заявки, названию гос. экзамена, названию колледжа и ФИО.
- Цвета — hex или rgb, без `oklch()`. Новые экраны берут цвета и размеры из переменных `site/css/app.css`. Код и картинки платного шаблона не копируются.
- Две темы, тёмная по умолчанию; каждый экран проверяется в обеих. Печать — всегда чёрным по белому.
- Студенческие экраны — для телефона шириной 360 px: без бокового меню, текст не мельче 16 px, кнопки и ссылки-кнопки не ниже 44 px.
- Настоящих данных студентов и сотрудников в репозитории нет: ни в коде, ни в тестах, ни в отчётах, ни на скриншотах, **ни в именах файлов Excel в тестах**. `dev/data/` и `build/` — в `.gitignore`.
- Локальный стенд — только порт 5273. Рабочий сервер (порт 5373), папки `D:\Журнал колледжа — сервер`, `D:\Журнал колледжа — данные`, `C:\JournalBackups`, файлы `serve.local.json` и `dev/data/real.json`, папка `dev/data/real-files/` агенты не открывают, не запускают и не правят.
- У пары вся группа целиком (подгрупп нет). 1 пара = 2 часа.
- Сообщения коммитов на английском; в конце строка `Co-Authored-By` с той моделью, которая на самом деле писала коммит. Агент коммитит **только свои файлы по имени** (не `git add -A`) и оставляет `git status` чистым.
- `git push` и обновление рабочего сервера — только по прямой просьбе владельца.
- **Данные студентов — строго.** Студент получает в ответе только своё: ни id, ни ФИО, ни баллов, ни результата гос. экзамена другого студента, ни заявок. Проверяется поиском по всему JSON ответа, а не только кодом ответа.
- **Права проверяются попыткой обойти защиту.** Отказ — и ничего не записано: тест сравнивает снимок таблиц до и после.
- **Журнал изменений** пишется в том же запросе; строки не меняются и не удаляются никогда.
- **Всё или ничего.** Запрос с одной плохой строкой не записывает ничего.
- Причина — текст до 300 знаков (`checkReason` из `core/journal.js`), хранится и показывается как текст.
- Стенд и браузер агентов: перед экранными задачами стенд координатора на 5273 остановлен, агент поднимает свой (`npm run dev:reset`). Браузер для проверки — только headless Chrome с временным профилем и ключами `--disable-sync --disable-extensions`; не Edge. Процессы агент останавливает **только по своему номеру (PID)** — те, что запустил сам; никогда по имени программы или заголовку окна. Браузер и учётные записи владельца агенты не трогают.
- Вход на стенде: `admin`, `dean` (деканат и преподаватель), `prorector`, `teacher1`…`teacher3`, студенты `S1001`…; пароль — константа `DEV_PASSWORD` в `dev/seed.js`. В отчётах и скриншотах пароль не пишется.

Новые правила юнита 6:

- **Числа ведомости — те же, что в журнале.** Ведомость берёт `current`, `self`, `control`, `total`, `word`, `currentLow`, `controlLow`, `preliminary` из `journalView` / `studentResults`; своей формулы ТК, СРС и итога юнита нет. Новая формула одна — итог предмета `finalResult` (задача 1), и при выставленных всех юнитах она даёт то же число, что `preliminary`.
- **Закрытый юнит не меняется никем напрямую.** Ключ закрытия — предмет + семестр по плану + юнит. Все пути записи из раздела «Кто что может менять» отвечают `unit_closed` и ничего не пишут — преподавателю, деканату и администратору одинаково. Единственный путь — заявка; единственный, кто открывает юнит заново, — администратор, с причиной.
- **Заявка применяется журналом, а не человеком.** `request.decide` сверяет «было» с базой на каждом шаге; не совпало — заявка закрывается как устаревшая (`stale`), ничего не меняется. Применение пишет данные, строки «Журнала изменений» (с `requestId` и причиной заявки) и состояние заявки одним запросом, в таком порядке.
- **Свою заявку не согласуют.** Ни автор, ни тот, кто согласовал первый шаг, не согласуют следующий — какие бы роли у них ни были. Администратор согласует шаг только тогда, когда других людей с нужной ролью нет (`mayDecide`, задача 2).
- **Таблицы пишут только свои модули:** «Закрытые юниты» — `backend/ledgerData.js`; «Заявки» — `backend/requestData.js`; «Гос. экзамены» и их результаты — `backend/stateExamData.js`; «Объявления» — `backend/announceData.js`; и `dev/seed.js` через их правила. «Посещаемость», «Итоги юнитов» и «Сдачи» при применении заявки пишутся только через функции своих модулей (`writeMarks`, `writeUnitResult` в `backend/journalData.js`, `applyPoints` в `backend/workGrade.js`). `dir.*` и импорт новых таблиц не знают.
- **Студент о заявках не знает ничего:** ни одно действие `request.*` и `ledger.*` студенту не доступно; в его ответах нет слова о заявке.
- **Запасной Apps Script:** юнит 6 работает там целиком (файлов он не добавляет), но применение заявки там — не одна запись: при обрыве правка может лечь без отметки «применена» (повторное согласование увидит, что «было» не совпадает, и закроет заявку как устаревшую). `npm run build:gas` собирается; живьём на Apps Script юнит 6 не проверяется.
- **Юниты 3–5 не меняются**, кроме прямо названного в задачах 6–8 и 12. Прежние тесты остаются зелёными без правок, кроме названных в задачах проверок списков таблиц, колонок, прав и одного ожидания `settings.get`. Новый ключ в прежнем ответе добавляется **только когда он есть** (`...(closed ? { closed: true } : {})`), чтобы прежние `deepEqual` оставались верными.
- **Проверка задач:** после каждой задачи 1–12 — облегчённая проверка (sonnet, короткий отчёт); **строгая** (обход, снимок таблиц, поиск в JSON) — задачи 2, 5, 7, 8, 9, 10, 11. Экранные: проверка ИИ — задачи 13, 15, 16, 18, 19, 20; задачи 14 и 17 владелец принимает блоком. Общая проверка — одна, в конце, строгая, opus.
- **Модели.** «Логика», «Сервер», «Экраны», проверяющий задач — sonnet; сверка плана и общая проверка — opus. Модель указывается явно в каждом поручении.

## Review Focus

1. **Чужая ведомость.** `teacher2` и заменяющий `teacher3` на предмете `teacher1`; прежний преподаватель после смены; проректор и студент: `ledger.get`, `ledger.closeUnit`, `ledger.closeFinal`, `ledger.reopen`. Читать чужую ведомость могут только деканат, проректор, администратор; закрывать — преподаватель предмета, деканат, администратор; открывать заново — только администратор. Отказ — снимок таблиц тот же. Тесты — задача 7.
2. **Закрытый юнит — каждый путь записи.** `journal.savePair` (преподаватель, заменяющий, деканат, администратор — в срок и после срока), `journal.saveResults` (три поля), `journal.reopenPair`, `lesson.start`, `work.grade`, `work.save`, `work.remove`, `work.submit`, `work.upload`, `scoring.save` — `unit_closed` / `units_closed`, ничего не записано. ДЗ закрытого юнита и соседний открытый юнит работают как раньше. Тесты — задача 8.
3. **Заявка: кто подаёт и кто согласует.** Преподаватель подаёт заявку на чужой предмет; на открытый юнит (`not_needed`); вторую такую же (`request_exists`); автор согласует свою (в том числе с ролью `dean` или `prorector`); один человек `dean,prorector` согласует оба шага; проректор согласует шаг деканата; администратор согласует, когда другой декан есть; преподаватель и студент вызывают `request.decide`; студент — любое `request.*`. Тесты — задачи 2, 9.
4. **Заявка: дважды и устарела.** Повторное «Согласовать» той же заявки (`request_closed`); согласование с устаревшим шагом (`request_changed`); «было» изменилось между подачей и согласованием → `stale`, данные не тронуты; балл больше максимума после смены схемы → `stale`; заявка на удалённого студента или пару, переставшую быть проведённой → `stale`. Тесты — задача 9.
5. **Заявка применена верно.** Каждый из пяти видов меняет ровно одно значение; строка «Журнала изменений» — с «было», «стало», причиной заявки, автором, `requestId`; итог юнита и ведомость после применения — числа раздела «Правила расчёта». Тесты — задача 9.
6. **Студент видит только своё.** `student.grades` (закрытые юниты, итог, гос. экзамены), `announce.list`, `work.get` — в JSON нет чужих id, ФИО, баллов; объявление другой группы и объявление «преподавателям» студент не получает; результат гос. экзамена другого студента — тоже. Тесты — задачи 8, 10, 11.
7. **Проректор не пишет.** Проректор: `ledger.close*`, `ledger.reopen`, `stateExam.save*`, `stateExam.remove`, `announce.save`, `announce.remove`, `settings.save` — `forbidden`; `request.decide` — только на своём шаге. Тесты — задачи 5, 7, 9–11.

9. **Плохие id.** `subjectId`, `unit`, `requestId`, `examId`, `studentId`, `groupId`, `id` — массив, число, объект, строка с пробелами, `'__proto__'`; `unit: '1'`; `after: 31` числом; `score: '90'`, `90.5`, `-1`, `101` — `not_found`, `bad_request` или `invalid`, ничего не записано, ответ не `internal`. ## Чего в юните 6 нет

- **Штрафов** за поведение и этику (вопрос 1): система оценивания не меняется до документа оценивания. Форма готова — `finalResult(units, scheme, penalty = 0)`; если владелец ответит «включить», координатор дописывает к плану задачу (таблица «Штрафы», ввод с причиной, вычитание из итога).

- **Замороженных чисел.** Закрытие ничего не копирует: число в закрытой ведомости — расчёт по тем же данным, которые закрытие запрещает менять.

- Заявок от деканата «за преподавателя»; подаёт только преподаватель предмета.

## Правила расчёта (с числами)

Схема по умолчанию: ТК 40, СРС 20, рубежный 40, минимум 24, пороги 60 / 76 / 90.

Итог предмета — `finalResult(units, scheme)`: если у студента есть итог **каждого** юнита — `Math.round(сумма / число юнитов)` и слово; иначе итога нет («не аттестован»).

| Студент | Юнит 1 (ТК + СРС + РК) | Юнит 2 | Предварительно (журнал) | Итог после закрытия итоговой |
| --- | --- | --- | --- | --- |
| a1 | 38 + 16 + 30 = **84** | 26 + 15 + 30 = **71** | 78 | **78** (77,5 → 78), «хорошо» |
| a2 | 20 + 12 + 25 = **57**, ТК 20 < 24 — подсвечен | 30 + 18 + 22 = **70**, РК 22 < 24 — подсвечен | 64 | **64** (63,5 → 64), «удовлетворительно» |

Правила `request.create`:

- `kind` не из `REQUEST_KINDS`, `after`/`before` не строки — `bad_request`. `subjectId` не строка или предмета нет — `not_found`. Право: роль `teacher` и `subject.teacherId === user.id`, иначе `forbidden`. Силлабуса нет — `no_syllabus`.
- Студент: `studentId` — строка, студент есть и он в списке журнала этого предмета (активный в группе или выбывший с данными), иначе `invalid` `studentId/bad_ref`.
- `current`, `self`, `control`: `unit` — целое из юнитов журнала (`unit/bad_value`); юнит закрыт, иначе `not_needed`; `self` у юнита по заданиям — `invalid` `unit/self_by_work`. «Сейчас» — действующее значение строки «Итогов юнитов» (`control`, `self`, `currentManual`) текстом. `after` — `parsePointsText`: `undefined` или `checkResultValue(kind, value, scheme)` не `null` — `invalid` `after/bad_value`.
- `mark`: `pairId` — строка, пара этого предмета внутри семестра (`not_found`); статус пары `closed`, иначе `pair_locked`. Юнит темы пары закрыт **или** срок правки прошёл (`markState === 'late'`), иначе `not_needed`; юнит открыт, срок прошёл и `limitedAllowed(было, стало)` — тоже `not_needed`. «Сейчас» — `markText` последней отметки студента на паре (`''`, если её нет). `after` — `parseMarkText`: не отметка — `after/bad_value`; `checkMark(было, стало, { mode: 'reason', pair, scheme })` вернул ошибки — `after/<первый код>`. `unit` заявки — юнит темы пары или `null`.
- `work`: `assignmentId` — строка, задание этого предмета (`not_found`); ДЗ или юнит не закрыт — `not_needed`. «Сейчас» — баллы текущей попытки студента текстом (`''`, если попытки нет или баллов нет); `attemptId` — её id или `''`. `after` — целое 0…`maxPoints` (не `''`), иначе `after/bad_value`.
- `before` запроса не равно «сейчас» — `invalid` `before/changed`. `after === before` — `invalid` `after/same`. Причина — `checkReason`, иначе `reason/<код>`.
- Есть открытая заявка с той же целью (`sameTarget`) — `request_exists`. У автора уже `REQUEST.openMax` открытых — `too_many`.
- Запись: одна строка «Заявок» `status: 'dean'`. В «Журнал изменений» при подаче ничего не пишется.

Правила `request.decide`:

- `requestId` не строка или заявки нет — `not_found`. Заявка не открыта — `request_closed`. `step !== request.status` — `request_changed`. `!mayDecide(request, { id, roles }, staff)` — `forbidden`. `verdict` не `'approve'` и не `'reject'` — `bad_request`.
- `reject`: `note` — `checkReason`, иначе `invalid` `note/<код>`. Заявка: `status: 'rejected'`, `closeNote`, `closedAt`; кто решил — `deanBy`/`deanAt` на шаге деканата, `finalBy`/`finalAt` на шаге проректора. Данные не меняются.
- `approve`: сначала проверка «не устарела» — теми же правилами, что при подаче, по нынешним данным: предмет, студент, пара (`closed`), задание существуют; «сейчас» равно `request.before` (у `work` — ещё и id текущей попытки равен `attemptId`); `after` по-прежнему допустимо. Не прошло — заявка `status: 'stale'`, `closedAt`; ответ `{ request, stale: true }`, **без ошибки** (иначе транзакция откатит и это).
- `approve` на шаге `dean`: `status: 'prorector'`, `deanBy`, `deanAt`. Ответ `{ request, stale: false }`.
- `approve` на шаге `prorector` — применение, в таком порядке: (1) данные — `mark`: `writeMarks` (источник `'teacher'`, `actorId` — автор заявки); `current`/`self`/`control`: `writeUnitResult`; `work`: `applyPoints`; (2) «Журнал изменений» одной `insertMany` — `mark`: по строке на изменившееся поле (`markChanges`), `entity: 'mark'`, `pairId`; юнит: `entity: 'unit'`, `field` — вид заявки; `work`: `entity: 'work'`, `field: 'points'` (и `field: 'status'`, если статус попытки изменился или попытка создана), `assignmentId`; у всех `actorId` — автор заявки, `reason` — причина заявки, `requestId`, `late: true`, `subjectId`, `studentId`, `unit`; (3) заявка: `status: 'applied'`, `finalBy`, `finalAt`, `closedAt`.
- `request.withdraw`: заявки нет — `not_found`; не автор — `forbidden`; не открыта — `request_closed`; иначе `status: 'withdrawn'`, `closedAt`.
- Каждая из `REQUEST_TABLES` читается один раз. Студент — ни одно действие (таблица прав).
