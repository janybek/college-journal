# Доработка «Силлабус дисциплины»: план сборки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** у дисциплины один силлабус на оба семестра, по нему идут все, кто её ведёт (из «Предметов»); деканат назначает ответственного и вписывает два срока; экран «Документы → Силлабусы» с вкладками «Утверждённые / На утверждении / В разработке»; нынешние силлабусы переносятся без потери тем проведённых пар, а где их несколько — деканат выбирает один.

**Architecture:** перестройка собранной, но нигде не выложенной серверной части «Общего силлабуса». Таблица «Линии силлабусов» становится «Силлабусами дисциплин» (вид `main` — силлабус дисциплины, `own` — прежний «свой» до выбора деканата, `archived` — история; в строке — ответственный и оба срока), таблица «Участники силлабусов» удаляется. Вопрос «по какому силлабусу идёт группа» по-прежнему решает одна функция `syllabusFor(subject, syllabi, half, lines)` — теперь через `lineFor` (дисциплина, а не «участник»); общий поиск во всех модулях, перенос при запуске и перекладка пар (`relayout` с «пропуском» `subjectScope`) остаются. Версия — это до двух строк «Силлабусов» одной линии (осень и весна): «Отправить», «Утвердить», «Вернуть» действуют на все половины сразу.

**Tech Stack:** как в прежних доработках — Node 24, ES-модули, `node --test`, встроенный `node:sqlite`, esbuild только для запасной сборки Apps Script, сайт без сборки. Новых зависимостей нет.

**Spec:** `aidlc-docs/construction/sillabus-discipliny/design.md` (решения владельца 1–8, «Уточнения после проверки дизайна» 1–9 и «Решения координатора» 1–8 обязательны). ## Global Constraints

Действуют все правила `.superpowers/sdd/plan-obshchiy-sillabus/implementer-contract.md` (раздел «Global constraints») — памятки копируются в `.superpowers/sdd/plan-sillabus-discipliny/` с этим разделом вместо правил «Общего силлабуса». Самое важное из них:

- `core/` и `backend/` без зависимостей из npm; обработчики синхронные; `handleRequest` никогда не бросает; ошибки — `AppError(code, { fields })`.
- Время — только `platform.now()`; даты — строки `'YYYY-MM-DD'`, дата со временем — `'YYYY-MM-DD HH:MM:SS'` (`localDateTime`).
- Каждая таблица читается не больше одного раза за запрос (`store.list`), запись пачкой; `store.get / update / remove` в цикле запрещены.
- Что попадает в сборку Apps Script, не содержит `node:`, `require(`, `Buffer`, слова `process` (`tests/gasBundle.test.js`); `npm run build:gas` зелёная после каждой задачи.
- Любая фраза — через три словаря `ru`, `ky`, `en` с одинаковыми ключами; данные на страницу — только текстом (`textContent`, помощники `site/js/ui.js`), никогда `innerHTML`; цвета hex или rgb, без `oklch()`; две темы, тёмная по умолчанию; студенческие экраны — 360 px, текст от 16 px, кнопки от 44 px.
- Настоящих людей нет нигде: ни в тестах, ни в отчётах, ни на скриншотах, ни на макетах. Стенд — только порт 5273; рабочий сервер (5373), `D:\Журнал колледжа — сервер`, `D:\Журнал колледжа — данные`, `C:\JournalBackups`, `dev/data/real.json` агенты не открывают и не правят.
- Стенд и браузер агентов: свой `npm run dev:reset`; headless Chrome с временным профилем и ключами `--disable-sync --disable-extensions`, не Edge; процессы останавливаются **только по своему PID**, никогда по имени программы или заголовку окна.
- Коммиты на английском, только свои файлы по имени (не `git add -A`), `git status` чистый; `git push` и выкладка — только по прямой просьбе владельца.
- Права проверяются попыткой обойти защиту; отказ — и ничего не записано (снимок **всех** таблиц до и после). Всё или ничего.

Новые правила доработки:

- **Один силлабус дисциплины.** У дисциплины не больше одной строки линии вида `main`. Каждый путь, который её заводит (перенос, первый черновик, загрузка файла, назначение ответственного, выбор), сначала ищет существующую (`mainLine`). Тесты задач 3–7 после каждого изменения вызывают `oneMain(store.list('syllabusLines'))` и ждут `[]`.
- **Силлабус группы — только через `syllabusFor(subject, syllabi, half, lines)`**, «линия группы» — только `lineFor`, «группы линии» — только `lineSubjects(subjects, line, lines, half)`, версии — только `versionsOfLine(syllabi, lineId, half)` (всегда с половиной). Сравнений `teacherId === version.teacherId` и вызовов `versionsOf` для поиска версии в `backend/` нет; `versionsOf` остаётся только внутри `nextVersion` и плана переноса.
- **Кто ведёт — только из «Предметов».** Ни одна таблица не хранит «участников»: «Ведут», «Преподаватели», права чтения — это предметы дисциплины на момент запроса. `subjects.add`, `dir.save` предмета и смена преподавателя группы не пишут в «Силлабусы дисциплин» (перекладывают пары прежним `relayout`, как сейчас).
- **Проведённая пара с темой держит свою тему.** Ни один путь (перенос, выбор, утверждение, назначение) не меняет `topicId`, `lessonType`, `part` пары со статусом `running` или `closed`, у которой тема есть, кроме переноса на копию той же темы при утверждении (как сейчас). Проведённая пара **без темы** получает следующую по счёту тему, как будущая (`layoutLessons`) — прежнее поведение. Все проверки «пары не изменились» ведутся по проведённым парам с темой.
- **Колонка «преподаватель» версии не пропадает и не переписывается.** У новой версии это `versionTeacher(...)` (уточнение 9: ответственный, если ведёт дисциплину; иначе ведущий с наибольшим числом пар, при равенстве — меньший id; никто не ведёт — ответственный или тот, кто начал). Смена ответственного, загрузка файла и сохранение разделов её не меняют. **Номер новой версии** = `nextVersion`: 1 + наибольший из номеров линии (обе половины) и номеров по старому ключу «дисциплина + этот `teacherId` + половина».
- **Порядок записи выбора, переноса и утверждения:** сначала новое, на что ещё никто не ссылается (новая строка линии), потом «Пары», потом «Силлабусы» (`lineId`, статусы), потом «Силлабусы дисциплин» (вид, ответственный, сроки) — чтобы оборванная запись (хранилища без транзакций) чинилась повтором того же запроса. На SQLite весь запрос — одна транзакция (`handleRequest`).
- **Таблицу «Силлабусы дисциплин» пишут только** `backend/linesUpgrade.js`, `backend/syllabusLines.js`, `backend/syllabusChoice.js`, `backend/syllabusFlow.js` (только очистка сроков после решения деканата) и `dev/seed.js` через их функции. `dir.*` и импорт её не знают (кроме запрета удаления).
- **Прежний сайт работает с новым сервером.** Сервер выкладывается раньше сайта: ни один ключ ответа, который читает сайт `857345c`, не убирается и не меняет смысл (`subject.teacherId`, `teacherName` очереди, `groups`, `semesters`, `state`, `can`, `syllabus` страницы; `syllabus.startDraft { subjectId, semester }`; `syllabus.queue`). Ключи, появившиеся только в «Общем» (`line.members`, `shared`, `authorName`, `lines` карточки, `can.newLine`), сайт не знает — их можно убирать. Новый ключ в прежнем ответе добавляется, только когда он есть.
- **Студент** получает о силлабусе дисциплины только `line: { teachers: [{ fullName }] }` — преподавателя **своей группы** (решение координатора 5): ни ответственного, ни сроков, ни других преподавателей (поиск по JSON ответа: `responsible`, `dueDate`, `reviewDue`, `createdBy`). Прежний ключ `subject.teacherId` (id преподавателя его группы) студент получает, как сейчас; других id сотрудников в ответе нет — внутри `line` id нет вовсе.
- **`plainId` не меняется.** Для него `'__proto__'` — обычная строка, а строка из пробелов может стать пустой: тесты на такой мусор ждут **отказ без записи** (`ok: false`, код не `internal`, снимок всех таблиц тот же), а не определённый код. Массив, число, объект, `null` — `bad_request`.
- **Сроки — только дата и цвет.** `dueDate` и `reviewDue` ничего не запрещают и не напоминают; «просрочено» считает сайт сравнением с `today` из ответа сервера.
- **Строк «Журнала изменений» доработка не пишет** (как «Общий»): следы — `createdBy` линии, `submittedBy`, `decidedBy` версий.

## Review Focus

1. **Чужая роль и мусор в параметрах.** `syllabus.assign`, `syllabus.setReviewDue`, `syllabus.choose`, `syllabus.startDraft { disciplineId }`, `syllabus.get { disciplineId }`, `docs.syllabi`, `docs.discipline` — каждой ролью и без входа: преподаватель другой дисциплины, ведущий вместо ответственного (править, отправить, «Заполнить из файла», файл версии), ответственный утверждает и назначает, проректор и студент — всё; `disciplineId`, `lineId`, `teacherId` — массив, число, объект, строка с пробелами, `'__proto__'`; даты — `'2026-13-45'`, число, массив. Ответ `forbidden`, `not_found`, `bad_request` или `invalid`, не `internal`; снимок всех таблиц тот же. Тесты — задачи 3–6.
2. **Потерянная или сменившаяся тема.** После переноса каждая группа, у которой темы были, видит те же (сравнение ответов `journal.get`, `ledger.list`, `syllabus.get`, `student.grades` до и после); перенос, выбор и утверждение не трогают проведённые пары с темой и пары чужих дисциплин; будущие пары продолжают «со следующей по счёту» по каждой группе отдельно; выбранный силлабус короче проведённого — будущие пары без темы, без ошибки. Тесты — задачи 3, 4, 6.
3. **Ответственный не тот, кем был.** Ответственного сменили, пока он правил (следующее сохранение — `forbidden`, текст не потерян у нового); ответственный не ведёт дисциплину, отключён (`active: false`), лишён роли преподавателя, удалён прежним кодом при откате (имя — пустая строка, не `internal`); два человека одновременно начинают первый черновик (ответственный — первый, второй получает `forbidden`, второй `main` не появился). Тесты — задачи 3, 5.
4. **Две половины в разных состояниях.** Осень — черновик, весна — на утверждении (после переноса): «Утвердить» действует только на отправленную; общая отправка выравнивает номер; неначатая половина не мешает отправить; файл на обе половины, когда одна на утверждении, — отказ целиком (`in_review`); студент не видит половину, пока её новая версия на утверждении, и не получает вместо неё другую. Тесты — задача 4.
5. **Перенос, выбор и откат.** Перенос повторяется без записи; база в виде «Общего» (линии без вида) переносится заново; версии, которые прежний код создал без `lineId`, встают на свои места и не дают второй утверждённой; закрытый юнит, итоговая и экзамен **текущей** половины запрещают выбор с названиями групп, прошлогодние — нет; выбор без утверждённой версии — только с подтверждением; прежний код `857345c` на новой базе не отвечает `internal`, ничего не стирает. Тесты — задачи 1, 3, 6, проба — задача 8.

## Решения плана, которые видят пользователи или которые меняют базу

Строки с пометкой «вопрос N» — вопросы `owner-summary.md` (по умолчанию — так, как здесь). Остальное — решения плана. Координатор переносит их в таблицу решений `aidlc-state.md` (задача 13, шаг 4).

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Таблицы и колонки | Лист «Линии силлабусов» становится «Силлабусы дисциплин» (ключ таблицы `syllabusLines` и колонки версии `lineId`, `sourceId` остаются); лист «Участники силлабусов» удаляется | нигде не выложены; ключ в коде не меняем — меньше правок |
| Где ответственный и сроки | В строке линии: `responsibleId`, `dueDate` (срок разработки), `reviewDue` (срок рассмотрения) | дизайн: «одна живая запись: дисциплина, ответственный, срок»; срок рассмотрения живёт, пока версия на утверждении |
| Несколько силлабусов после переноса | У каждого прежнего — линия вида `own` (чей, какая половина). Невыбранные после выбора — вид `archived` | дизайн, «Перенос» п. 2 |
| **Одна половина ждёт выбора, в другой силлабус один (вопрос 1)** | Половина с одним силлабусом сразу действует для всех групп дисциплины; половина с несколькими ждёт выбора. Ответственный у дисциплины появляется, когда выбора не ждёт ни одна половина; до этого каждый прежний силлабус правит его преподаватель | дизайн молчит о смешанном случае; так «ничего не меняется» только там, где есть спор |
| Что происходит с невыбранными (и с проигравшими при переносе) | Все незаконченные версии — черновик, возвращённая и **на утверждении** — получают статус «архив» (дизайн, уточнение 6, дополнено при сверке плана); утверждённая **статус не меняет**, но линия — история: по ней никто не идёт, на экране она в «Истории» как «прежний силлабус: Фамилия И.» | откат: прежний код покажет преподавателю его прежний утверждённый, как требует дизайн |

## Модель данных

`core/schema.js` (задача 3): константа `LINE_KINDS` вместо `MEMBER_STATES`; таблица `syllabusMembers` удаляется (таблиц 37 → 36); `syllabusLines` — новый лист и колонки; у `syllabi` подпись колонки `lineId` — «силлабус дисциплины».

```js
export const LINE_KINDS = ['main', 'own', 'archived'];   // силлабус дисциплины; прежний «свой» до выбора деканата; история
syllabusLines: { sheet: 'Силлабусы дисциплин', prefix: 'sl', columns: [
  id, disciplineId 'дисциплина', kind 'вид', semester 'половина года' int, teacherId 'преподаватель',
  responsibleId 'ответственный', dueDate 'срок разработки', reviewDue 'срок рассмотрения', createdBy 'кто завёл', createdAt 'когда заведён' ] },
```

- `main`: `semester` — `null`, `teacherId` — `''`; `responsibleId` — id сотрудника или `''` («не назначен»); `dueDate`, `reviewDue` — `'YYYY-MM-DD'` или `''`. Версии обеих половин несут её `lineId`.
- `own` и `archived`: `semester` 1 или 2, `teacherId` — чей был силлабус; `responsibleId`, `dueDate` пустые; `reviewDue` у `own` работает (его версию тоже рассматривают).
- **И1:** у дисциплины не больше одной `main`. **И2:** не больше одной `own` на «дисциплина + половина + преподаватель». **И3:** у линии `main` или `own` в одной половине не больше одной утверждённой версии и не больше одной открытой; у каждой версии с полным ключом после запуска сервера есть `lineId`; лишнюю утверждённую (появляется только после отката) запуск отправляет в архив. **И4:** половина «ждёт выбора» ⇔ в ней больше одной `own`.
- Строка линии без вида (`kind === ''`) — от «Общего» (только файлы стенда): перенос её удаляет и переносит её версии заново по колонке «преподаватель».
- `sourceId` версии — как было: id утверждённой версии, с которой скопирован черновик.

**Что известно заранее (записать в раздел выкладки `aidlc-state.md`; проба уточняет):** на прежнем коде силлабус дисциплины виден как «свой» тому, чей id стоит в колонке «преподаватель» версии (ответственный, если ведёт; иначе ведущий с наибольшим числом пар); остальные ведущие видят свой прежний утверждённый (если был — у невыбранных он остаётся «утверждён») или группы без тем; «Документов», ответственного и сроков нет. Правила:

- **`openDrafts`.** У линии нет открытых строк: черновик-копия заводится для **каждой** половины, где у линии есть утверждённая версия, и пустой — для запрошенных половин без утверждённой; у всех один номер `nextVersion`. Линия `own` — одна половина, поведение прежнее.
- **Начатая половина** — открытая строка, у которой есть хоть одна строка плана («Темы») или утверждённая версия той же половины.
- **`syllabus.submit`**: цели — все открытые строки линии в статусе `draft` или `returned`, которые начаты, и всегда — строка запроса. Проверки (`examine`) — по каждой; ошибки и предупреждения складываются, при нескольких целях каждая получает `semester`. Есть ошибка или `dryRun` — ничего не записано.
