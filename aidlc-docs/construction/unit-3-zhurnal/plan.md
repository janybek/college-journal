# Юнит 3 «Журнал и оценки»: план сборки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** преподаватель сам ведёт журнал «студенты × даты пар» по своему предмету и группе: статусы явки, «без халата», активность, рубежный контроль и СРС юнита; текущий контроль юнита журнал считает сам; каждое изменение отметки и оценки пишется в журнал изменений; деканат видит все журналы и незаполненные пары; студент на телефоне видит свои баллы и пропуски. QR, код, «Я на паре» и экран пары с таймером — юнит 4, поверх этого журнала.

**Architecture:** правила (схема баллов, расчёт баллов за пару и текущего контроля, срок правки, что кому можно менять) — чистые функции в `core/`. Сервер (`backend/journalData.js`, `backend/studentGrades.js`, обработчики `journal.*`, `scoring.*`, `student.grades`) читает каждую таблицу один раз за запрос, считает через `core/` и пишет пачкой; в ответ после любой записи отдаёт журнал предмета заново. Три новые таблицы: «Посещаемость», «Итоги юнитов», «Журнал изменений»; у «Пар» новая колонка «замена»; числа схемы баллов — строки в «Настройках». **Баллы за пару, текущий контроль и итоги не хранятся: они считаются при каждом чтении** из посещаемости и схемы. Сайт получает экраны: список журналов, сетка журнала, окно отметки пары, окно ячейки, окна итогов юнита, «Журнал изменений», карточка «Баллы и журнал» в «Настройках», «Оценки» студента.

**Tech Stack:** как в юните 2 с доработкой 4 — Node 24, ES-модули, `node --test`, встроенный `node:sqlite` (рабочий сервер), esbuild только для запасной сборки под Apps Script, сайт без сборки. Новых зависимостей нет.

**Spec:** `aidlc-docs/inception/design-v1.md` (раздел 6: «Пара и отметка», «Баллы за пару и текущий контроль», «Ведомость (вариант А)»; раздел 8), `aidlc-docs/inception/ТЗ.md` (разделы 2, 5, 6, 11), таблица решений `aidlc-docs/aidlc-state.md` — строки от 22.11.2026: «Порядок юнитов меняется», «Новые правила (приняты все 12)» (правила 5, 6, 7, 8, 9, 12). Где этот план расходится с `design-v1.md`, действует план (см. «Решения плана»).

**Исходное состояние:** `HEAD 0b9824b`, 591 тест, `npm run build:gas` собирается. Юнит 2 с доработками 1–4 выложен; в рабочей базе — пробные данные.

**Порядок.** Перед задачей 1 — сверка плана проверяющим на самой сильной модели (задачи между собой и с готовым кодом: имена, поля, существующие тесты, которые сломаются); находки правит отдельный агент в этом файле. Затем задачи 1 → 21 строго по одной, после каждой `npm test` зелёное и `npm run build:gas` собирается. **После задачи 16 — скриншоты сетки журнала владельцу и стоп до его ответа.** После задачи 21 — общая проверка юнита, одна волна исправлений, повторная проверка, показ владельцу (задача 22).

## Global Constraints

Действующие правила юнита 2 (переносятся без изменений):

- `core/` и `backend/` без зависимостей из npm. Dev-зависимости проекта: `esbuild`, `xlsx`, `@fontsource-variable/inter`. Новые не добавляются.
- Сайт: без сборки, без фреймворков, ничего не загружает с чужих адресов (ни CDN, ни внешних шрифтов).
- Все обработчики сервера синхронные. `handleRequest` никогда не бросает исключение и всегда возвращает объект ответа. Ошибки — `AppError(code, { fields })` из `core/errors.js`.
- Запрос сайта: `POST`, `Content-Type: text/plain;charset=utf-8`, тело — JSON `{action, token, data}`. Своих заголовков нет.
- `passwordHash` никогда не попадает в ответ сервера. Ответы собираются по полям; строки сотрудников и студентов в ответ целиком не копируются.
- Время берётся только из `platform.now()`. `Date.now()` и `new Date()` без аргумента в `core/` и `backend/` запрещены. «Сегодня» — `localDate(platform.now())` по Бишкеку (UTC+6 круглый год). Сайт часам устройства не доверяет: «сегодня» и «сейчас» он берёт из ответа сервера.
- Дата — строка `'YYYY-MM-DD'`, время — `'HH:MM'`, дата со временем — `'YYYY-MM-DD HH:MM:SS'` (новая, `localDateTime`). Объектов `Date` в строках хранилища нет.
- В базе хранятся английские коды (`present`, `closed`), на экране они переводятся словарём.
- Обработчик читает каждую таблицу не больше одного раза за запрос (`store.list`) и пишет пачкой (`insertMany`, `updateMany`, `removeMany`). `store.get`, `store.update`, `store.remove` в цикле запрещены. На SQLite это не вопрос скорости, но код остаётся рабочим и на запасном Apps Script.
- Что попадает в сборку Apps Script, остаётся чистым: `backend/api.js`, `backend/handlers/*`, `backend/*.js` (кроме `backend/node/` и `backend/store/sqliteStore.js`), `core/*` не импортируют ничего из `backend/node/`; в них нет `node:`, `require(` и слова `process` даже в комментариях (их ищет `tests/gasBundle.test.js`).
- Роли: `admin`, `dean`, `prorector`, `teacher`, `student`. У сотрудника роли хранятся строкой через запятую; у одного человека может быть несколько ролей (`dean,teacher`).
- Любая фраза на экране идёт через ключ словаря. Наборы ключей в `ky`, `ru`, `en` одинаковые (`tests/i18n.test.js`). Названия дней и месяцев — из словаря, без `Intl`.
- Данные с сервера, от пользователя и из файлов попадают на страницу только как текст (`textContent`, помощники из `site/js/ui.js`), никогда через `innerHTML`. Это относится и к причинам правок, и к ФИО.
- Цвета — hex или rgb, без `oklch()`. Новые экраны берут цвета и размеры из переменных `site/css/app.css`. Код и картинки платного шаблона не копируются.
- Две темы, тёмная по умолчанию; каждый экран проверяется в обеих.
- Студенческие экраны — для телефона шириной 360 px: без бокового меню, текст не мельче 16 px, кнопки и ссылки-кнопки не ниже 44 px.
- Настоящих данных студентов и сотрудников в репозитории нет: ни в коде, ни в тестах, ни в отчётах, ни на скриншотах. Данные стенда вымышленные. `dev/data/` и `build/` — в `.gitignore`.
- Локальный стенд — только порт 5273. Рабочий сервер (порт 5373), папки `D:\Журнал колледжа — сервер`, `D:\Журнал колледжа — данные`, `C:\JournalBackups`, файлы `serve.local.json` и `dev/data/real.json` агенты не открывают, не запускают и не правят.
- У пары вся группа целиком (подгрупп нет — правило 5 владельца, по умолчанию). 1 пара = 2 часа.
- Сообщения коммитов на английском; в конце строка `Co-Authored-By` с той моделью, которая на самом деле писала коммит. Агент коммитит **только свои файлы по имени** (не `git add -A`) и оставляет `git status` чистым.
- `git push` и обновление рабочего сервера — только по прямой просьбе владельца.

Новые правила юнита 3:

- **Данные студентов — строго.** Студент получает в ответе только свои отметки и баллы: ни id, ни ФИО, ни отметок другого студента нет ни в одном поле. Преподаватель получает журнал только своего предмета; по чужому предмету, где он вёл отдельные пары (замена, прежний преподаватель), — только эти пары, без итогов юнитов. Проректор только смотрит. Это проверяется в тестах поиском по всему JSON ответа, а не только кодом ответа.
- **Права проверяются попыткой обойти защиту:** чужой предмет, чужая группа, чужая пара, студент другой группы в списке отметок, массив, число или строка с пробелами вместо id, будущая, отменённая и просроченная пара. Отказ — и ничего не записано: тест сравнивает снимок таблиц «Посещаемость», «Итоги юнитов», «Журнал изменений» и «Пары» до и после.
- **Журнал изменений (правило 6 владельца).** Любое изменение уже сохранённой отметки (статус, «без халата», активность), любая запись рубежного, СРС и ручного текущего контроля, «не проведена», возврат и сброс отметок пары пишут строки в «Журнал изменений» **в том же запросе** (на рабочем сервере — в той же транзакции): кто, когда, было → стало, причина, признак «после срока». Первая отметка пары в журнал изменений не пишется: кто и когда — в самой строке «Посещаемости». Таблицы «Посещаемость», «Итоги юнитов» и «Журнал изменений» пишет только `backend/journalData.js` (и `dev/seed.js` через его функции); `dir.save`, `dir.remove` и импорт этих таблиц не знают. Строки «Журнала изменений» не меняются и не удаляются никогда.
- **Всё или ничего.** Запрос с одной плохой строкой (плохой статус, чужой студент, нет причины) не записывает ничего.
- **Расчёт — при чтении.** Баллы за пару, текущий контроль, итог юнита и проценты посещаемости нигде не хранятся. Схема баллов одна на колледж (правило 8), её числа лежат в «Настройках»; силлабус её только показывает.
- **Причина правки** — текст до 300 знаков, без переводов строк по краям; хранится и показывается как текст.
- **Проверка задач (правило 12 владельца).** Проверка каждой задачи облегчённая: sonnet, короткий отчёт, пробы только на права и данные студентов. Для задач 9–13 (сервер журнала) пробы на права и «ничего не записано» обязательны всегда. Общая проверка юнита — строгая, самой сильной моделью, с пробными скриптами против настоящего кода.
- **Модели.** «Логика», «Сервер», проверяющий — sonnet. «Экраны»: новые экраны (задачи 16–19, 21) — opus; карточка в готовом экране и экран-таблица по образцу (задачи 15, 20) — sonnet. Сверка плана и общая проверка — самая сильная модель. Модель указывается явно в каждом поручении.
- **Стенд и браузер агентов.** Перед экранными задачами стенд координатора на 5273 остановлен: агент поднимает свой (`npm run dev:reset`). Браузер для проверки — только headless Chrome с временным профилем и ключами `--disable-sync --disable-extensions`; не Edge. Процессы агент останавливает **только по своему номеру (PID)** — те, что запустил сам; никогда по имени программы или заголовку окна. Браузер и учётные записи владельца агенты не трогают.
- Вход на стенде: `admin`, `dean` (деканат и преподаватель), `prorector`, `teacher1`…`teacher3`, студенты `S1001`…; пароль — константа `DEV_PASSWORD` в `dev/seed.js`. В отчётах и скриншотах пароль не пишется.

## Review Focus

1. **Чужой журнал.** Преподаватель не читает и не правит журнал чужого предмета ни с экрана, ни прямым запросом с чужим `subjectId` или `pairId`; заменяющий видит и правит только свою пару и не получает итогов юнитов; проректор ничего не меняет; студент не вызывает ни одного действия `journal.*`. Тесты — задачи 9, 10, 11, 12.
2. **Студент и чужие баллы.** `student.grades` не читает из запроса ничего: чужой `studentId`, `groupId`, `subjectId` в данных запроса не меняют ответ; в JSON ответа нет ни одного чужого id и ФИО. Тесты — задача 13.
3. **Не тот id.** Массив, число, объект, строка с пробелами вместо `pairId`, `subjectId`, `studentId`; студент другой группы или выключенный студент в списке отметок; один студент дважды — отказ, ничего не записано. Тесты — задачи 10, 11, 12.
4. **Срок правки.** До звонка пары отметки не ставятся; в срок преподаватель правит свободно; после срока незаполненную пару он заполнить не может, в заполненной делает только два изменения с причиной («не был» → «уважительная причина»; «не был» или «уважительная причина» → «отработано» с активностью); деканат и администратор меняют всё, но всегда с причиной. Граница срока — конец дня по Бишкеку (запрос в 00:30 по Бишкеку — уже следующий день). Тесты — задачи 4 и 10.
5. **Журнал изменений полон.** После каждого изменения сохранённой отметки, рубежного, СРС, ручного текущего контроля, «не проведена», возврата и сброса в «Журнале изменений» есть строка с верными «было», «стало», автором и причиной; при отказе строк нет; повтор того же значения строк не создаёт. Тесты — задачи 10, 11, 12.
6. **Расчёт.** Первая пара предмета — только явка; рубежная пара в текущий контроль не входит; «уважительная причина» и пара без отметки не входят в расчёт; «отработано» даёт явку и активность; округление половины вверх; ручной текущий контроль перекрывает расчётный и снимается; пары без темы — вне юнитов; итог юнита появляется только при выставленных СРС и рубежном. Числа — из раздела «Правила расчёта». Тесты — задачи 3, 9, 13.
7. **Схема баллов.** Сумма «текущий + СРС + рубежный» не равна 100, пороги не по возрастанию, не числа — ошибка у поля, ничего не записано; испорченные строки «Настроек» дают схему по умолчанию; сохранение настроек семестра не трогает числа схемы и наоборот; после смены чисел журнал пересчитан. Тесты — задачи 1 и 7.
8. **Проведённая пара и темы.** Сохранение отметок делает пару проведённой (`closed`), её тема закрепляется; проведённая пара без темы получает тему при следующей раскладке; «не проведена» отдаёт тему следующей непроведённой паре; сброс отметок возвращает пару в расписание. Прежние защиты силлабуса (тему проведённой пары нельзя убрать) работают на парах, проведённых через журнал. Тесты — задачи 5, 10, 12.
9. **Замена и смена преподавателя.** Прошедшие пары прежнего преподавателя не помечены «Замена»; разовая замена помечена и после того, как пара проведена и преподаватель предмета сменился; отметки на паре замены ставит и заменяющий, и преподаватель предмета. Тесты — задачи 5, 8, 10.
10. **Курс и семестр (правило 7).** «2 курс 1 семестр» в файле читается как семестр 3 с замечанием; титул, где курс не сходится с семестром по плану, не отправляется и не утверждается; группа другого курса — предупреждение при отправке и утверждении. Тесты — задачи 6 и 8.
11. **Запрет удаления.** Студента с отметками или итогами, сотрудника, который ставил отметки или записан в журнале изменений, предмет с итогами юнитов удалить нельзя (`in_use`); пары с отметками не удаляются пересозданием расписания. Тесты — задача 8.
12. **Выбывший студент.** Студент, переведённый в другую группу или выключенный, не пропадает из журнала молча: его прежние отметки видны строкой «выбыл», в расчёты других студентов он не входит. Тесты — задача 9.
13. **Одно чтение каждой таблицы.** `journal.get`, `journal.savePair`, `journal.saveResults`, `student.grades` читают каждую таблицу один раз и пишут не больше одной пачки каждого вида на таблицу. Тесты со шпионом — задачи 9, 10, 11, 13.
14. **Алфавит.** Список студентов журнала стоит по алфавиту с Ё после Е, Ң после Н, Ө после О, Ү после У, без учёта регистра. Тесты — задачи 3 и 9.
15. **Экраны.** Сетка на 22 студента и 40 пар прокручивается внутри таблицы, первая колонка на месте; двойное нажатие «Сохранить» не шлёт два запроса; ответ, пришедший после ухода со страницы, ничего не рисует; несохранённые отметки и уход со страницы; текст причины с `<script>` и `=СУММ()` остаётся текстом; студент на телефоне 360 px без горизонтальной прокрутки страницы. Проверка на стенде — задачи 16–21.

Проверяющий задач 9–13 отдельно убеждается: каждая проверка «ничего не записано», «каждая таблица один раз», «в ответе нет чужого студента» написана настоящим `assert` по данным, а не комментарием и не проверкой кода ответа.

## Решения плана, которые видит пользователь или которые меняют базу

Координатор показывает их владельцу вместе с `owner-summary.md` и после согласия переносит в таблицу решений `aidlc-state.md`. Строки с пометкой «вопрос N» вынесены владельцу; в плане стоит вариант по умолчанию.

| Вопрос | Решение по умолчанию | Почему |
| --- | --- | --- |
| Когда пара «проведена» (вопрос 1) | Когда по ней первый раз сохранены отметки: статус пары `closed`. Кнопки «Пара проведена» нет | меньше действий, чем с бумажным журналом |
| Отметка по умолчанию | В окне первой отметки все стоят «был»; преподаватель меняет только отсутствующих и опоздавших и нажимает «Сохранить». Сохраняются отметки сразу всем студентам группы | как в бумажном журнале пишут только «н» |
| С какого момента можно отмечать | Со звонка пары (время начала) в её день. Раньше — отказ | нельзя отметить пару, которой ещё не было |
| Срок свободной правки (вопрос 1) | День пары и ещё 3 дня (число — `journalEditDays` в «Настройках», 0–60) | пятничную пару можно заполнить в понедельник |
| После срока — преподаватель | Незаполненную пару не заполняет («обратитесь в деканат»). В заполненной — только два изменения с обязательной причиной: «не был» → «уважительная причина»; «не был» или «уважительная причина» → «отработано» с активностью | `design-v1.md`, раздел 6 |
| Деканат и администратор (вопрос 4) | Могут заполнить пару и исправить любую отметку и балл в любой день; причина обязательна всегда; всё пишется в журнал изменений. Проректор только смотрит | заявок на исправление ещё нет (юнит 6) |
| Прошедшая пара без отметок (вопрос 2) | Остаётся в расписании со статусом `planned` и в журнале показана «не заполнена»; тема с неё не уходит. «Не проведена» (`missed`) ставит только деканат или администратор вручную, с причиной — тогда тема переходит на следующую непроведённую пару. Сама пара «не проведена» не становится | журнал начинают вести посреди семестра и заполняют с опозданием; автоматический сдвиг тем сломал бы всё расписание тем |
| Список незаполненных пар | В списке журналов у каждого предмета число незаполненных пар и сколько из них просрочено | деканат видит, кто не ведёт журнал |
| Сброс отметок пары | Деканат или администратор, с причиной: отметки пары удаляются (каждая — строкой в журнале изменений), пара снова «не заполнена» | преподаватель отметил не ту пару |
| Замена (вопрос 5) | Отметки на паре ставит тот, кто её провёл, и преподаватель предмета — оба свободно в срок. Заменяющий видит в журнале предмета только свои пары, без итогов | не блокировать ни одного из двоих |
| Схема баллов | Одна на колледж, числа в «Настройках» (карточка «Баллы и журнал»): явка 20, активность до 10, текущий 40, СРС 20, рубежный 40, зачётный минимум 24, пороги 60 / 76 / 90, срок правки 3 дня. Меняют деканат и администратор. Смена чисел пересчитывает все журналы сразу | правило 8 владельца |
| Баллы за пару | Как в `design-v1.md`: первая пара предмета — только явка; рубежная пара — без баллов; «уважительная» не входит в расчёт. Подробно — «Правила расчёта» | решение владельца |
| СРС юнита (вопрос 3) | Преподаватель вводит балл СРС за юнит числом (0–20), как рубежный. В юните 5 балл начнёт считаться по заданиям; ручной останется для юнитов без заданий | иначе до юнита 5 нет итога юнита |
| Итог юнита и предмета | Итог юнита = текущий + СРС + рубежный; показывается, когда выставлены и СРС, и рубежный. По предмету — «предварительно»: среднее по юнитам с итогом, с оценкой словом. Итог «в зачёт», штрафы и закрытие юнита — в «Ведомостях» | `design-v1.md`, «Ведомость (вариант А)» |
| Ручная правка текущего контроля | Преподаватель предмета (и деканат) ставит своё число вместо расчётного, причина обязательна; можно вернуть расчётное. Пока юнит не закрывается (закрытие — юнит 6), правка доступна всегда | ТЗ, раздел 5 |
| Зачётный минимум | Текущий или рубежный ниже 24 подсвечены в журнале и у студента | ТЗ, раздел 5 |
| Пара без темы | Отмечать можно; её баллы показаны отдельно («вне юнитов») и в текущий контроль не входят, пока у пары нет темы. Проведённая пара без темы получает тему при следующей раскладке (например, когда деканат утвердит силлабус) | починка (1) из доработки 3 |
| Студент видит (вопрос 8) | По каждому предмету: баллы юнитов, «предварительно», сколько пар был и пропустил, список своих пар с отметкой и баллами. Чужого не видит | решение владельца |
| Курс и семестр (правило 7) | Титул силлабуса: семестр по плану должен быть семестром этого курса (1 курс — 1 и 2, 2 курс — 3 и 4…), иначе не отправить. «2 курс 1 семестр» в файле — семестр 3 с замечанием. Группа другого курса — предупреждение | правило 7 владельца |

На живом сайте — перезалить пробные данные командой `npm run serve:demo-wipe` после выкладки; отдельной команды «долить оценки» нет | готовый код; пробная база и так под очистку |

Новые константы и таблицы в `core/schema.js` (задача 2). Таблицы дописываются в конец `SCHEMA`, после `pairs`.

```js
export const ATTENDANCE_STATUSES = ['present', 'late', 'absent', 'excused', 'madeup'];   // был, опоздал, не был, уважительная причина, отработано
export const ATTENDED_STATUSES = ['present', 'late', 'madeup'];
```

Смысл:

- **Посещаемость** — одна строка на «пара + студент». `activity` — пусто (`null`) или 0…максимум. `source` в юните 3 всегда `teacher`. `markedBy` — id сотрудника, который записал или последним изменил строку; `markedAt` — `'YYYY-MM-DD HH:MM:SS'`. Если в таблице оказались две строки одной пары и студента, читается последняя по `markedAt`, затем по id (правило чтения, запись дублей не создаёт).
- **Итоги юнитов** — одна строка на «предмет + студент + семестр по плану + юнит». `control` — рубежный, `self` — СРС, `currentManual` — ручной текущий контроль; пусто — не выставлено. «Семестр по плану» (1–8) берётся из утверждённого силлабуса, по которому идёт предмет в текущей половине года: так юнит 1 третьего семестра не смешается с юнитом 1 первого.
- **Журнал изменений** — только добавление. `entity`: `mark` (отметка студента на паре; `field` — `status`, `noCoat`, `activity`), `unit` (итог юнита; `field` — `control`, `self`, `current`), `pair` (статус пары; `field` — `status`). `before` и `after` — текст: код статуса; `yes`/`no` для «без халата»; число; пустая строка для «не было». `late` — правка после срока свободной правки. `at` — `'YYYY-MM-DD HH:MM:SS'`.
- **Пары, «замена»** — истина, если пару ведёт не преподаватель предмета по разовой замене. Ставится при замене и закрепляется, когда пара проведена (задачи 5, 8, 10).
- **Юнит пары** — юнит темы, которая стоит на паре (`topics.unit` по `pairs.topicId`); у пары без темы юнита нет.
- **Настройки** — десять новых ключей (значение — целое число текстом): `scoreAttendance`, `scoreActivity`, `scoreCurrent`, `scoreSelf`, `scoreControl`, `scoreMinimum`, `scoreFair`, `scoreGood`, `scoreExcellent`, `journalEditDays`. Строки появляются при первом сохранении карточки; пока их нет, действует схема по умолчанию.

Что заложено для юнита 4 (без переделки): отметка студента — та же строка «Посещаемости» с `source` `code` или `qr` и `markedBy` = id студента; колонку «устройство» в «Посещаемость», «фактический старт» и «секрет QR» в «Пары» допишет юнит 4 (хранилища дописывают колонки сами); статус `running` уже учитывается расчётом как «проведена»; запись отметок идёт через одну функцию `writeMarks` с параметром `source`.

## Правила расчёта (с числами)

Схема по умолчанию: явка **20**, активность **0–10**, текущий контроль **40**, СРС **20**, рубежный **40**, зачётный минимум **24**, пороги **60 / 76 / 90**.

Баллы студента за одну проведённую пару (`closed`, в юните 4 ещё `running`):

| Случай | Набрано | Возможно | Входит в текущий контроль |
| --- | --- | --- | --- |
| был, опоздал, отработано; обычная пара | 20 + активность (пусто = 0) | 30 | да |
| не был; обычная пара | 0 | 30 | да |
| первая пара предмета: был, опоздал, отработано | 20 (активности нет) | 20 | да |
| первая пара предмета: не был | 0 | 20 | да |
| уважительная причина | — | — | нет, пока не станет «отработано» |
| у студента нет отметки на этой паре | — | — | нет |
| рубежная пара (тип занятия `control`) | — | — | нет: явка отмечается, баллов нет |
| пара не проведена, отменена, не заполнена | — | — | нет |

- **Первая пара предмета** — самая ранняя (дата, № пары, id) пара предмета в датах текущего семестра со статусом `planned`, `running` или `closed`. Отменённая и «не проведена» первой не считаются.
- **Текущий контроль юнита** = сумма набранного / сумма возможного × 40 по парам этого юнита, округление до целого (`Math.round`: половина вверх). Возможного нет — текущего контроля нет (пусто).
- Пары без темы (без юнита) считаются так же, но показываются отдельно («вне юнитов») и в юниты не входят.
- **Ручной текущий контроль** перекрывает расчётный; расчётный показывается рядом.
- **Итог юнита** = текущий + СРС + рубежный; пусто, пока не выставлены и СРС, и рубежный (и есть текущий).
- **Оценка словом:** до 59 — `fail` (неуд.), 60–75 — `fair` (удовл.), 76–89 — `good` (хорошо), 90–100 — `excellent` (отлично).
- **Предварительно по предмету** — среднее итогов юнитов, у которых итог есть, округление до целого; ни одного — пусто.
- **Ниже минимума:** текущий < 24 или рубежный < 24 (когда значение есть).
- **Посещаемость:** `marked` — число проведённых пар, где у студента есть отметка (рубежные входят); `attended` — был + опоздал + отработано; процент = `attended / marked × 100`, округление до целого; `marked = 0` — пусто.
- Сохранённая активность больше нынешнего максимума (схему уменьшили) считается как максимум.

Пример (юнит 1, обычные пары, кроме первой):

| Пара | Отметка | Набрано / возможно |
| --- | --- | --- |
| 1 (первая пара предмета) | был | 20 / 20 |
| 2 | был, активность 7 | 27 / 30 |
| 3 | опоздал, активность 5 | 25 / 30 |
| 4 | не был | 0 / 30 |
| 5 | уважительная причина | не входит |

Набрано 72 из 110 → 72 / 110 × 40 = 26,18 → **текущий контроль 26**. Студент отработал пару 5 с активностью 8 (28 / 30): 100 из 140 → 28,57 → **29**. СРС 16, рубежный 30 → **итог юнита 75, «удовлетворительно»**; при рубежном 31 — 76, «хорошо».

### Task 4 (Л): правила отметки — срок и что можно менять

**Files:** Create `core/journal.js`, `tests/journalRules.test.js`.

**Interfaces — Consumes:** `addDays` (`core/dates.js`), `ATTENDANCE_STATUSES`, `ATTENDED_STATUSES`, `FIXED_STATUSES`, `REASON_MAX`.

```js
export function markState(pair, now, scheme);
// -> 'cancelled' | 'missed' | 'future' | 'open' | 'late'
//    cancelled, missed — по статусу пары; future — день пары ещё не настал или настал, но now.time < pair.startTime;
//    open — now.date <= addDays(pair.date, scheme.editDays); иначе late

export function markMode({ state, held, teacher, manager });
// held: пара проведена (статус в FIXED_STATUSES); teacher: человек ведёт эту пару или предмет; manager: администратор или деканат
// -> 'free' (любая правка без причины) | 'reason' (любая правка, причина обязательна) | 'limited' (два изменения с причиной) | 'none'
//    future, cancelled, missed -> 'none';  teacher и open -> 'free';  иначе manager -> 'reason';  иначе teacher, late и held -> 'limited';  иначе 'none'

export function normalizeMark(input);            // -> { status, noCoat, activity } | null (вход не объект; status не строка; noCoat не boolean и не undefined; activity не целое, не null и не undefined)
export function checkMark(old, next, { mode, pair, scheme });

export function markChanges(old, next);          // -> [{ field: 'status' | 'noCoat' | 'activity', before, after }] — только изменившиеся поля, значения текстом
export function checkReason(reason);             // -> 'required' | 'too_long' | null (строка после trim: 1…REASON_MAX знаков)
export function checkResultValue(field, value, scheme);   // field из RESULT_FIELDS; value: null или целое 0…максимум поля -> 'bad_value' | null
```

Правила `checkMark`:

- `status` не из `ATTENDANCE_STATUSES` — `{ field: 'status', code: 'bad_value' }`.
- `activity` не `null`, когда статус не из `ATTENDED_STATUSES`, или пара первая (`pair.first`), или рубежная (`lessonType === 'control'`) — `{ field: 'activity', code: 'not_allowed' }`; вне 0…`scheme.activity` — `bad_value`.
- Режим `limited`: разрешено только `old.status === 'absent'` → `excused` (без активности) и `old.status` из `absent`, `excused` → `madeup` (активность по правилам выше); `noCoat` не меняется. Всё остальное, что меняет отметку, и `old === null` — `{ field: 'status', code: 'locked' }`.
- Режим `none` — `{ field: 'status', code: 'locked' }` при любом изменении.
- Отметка без изменений ошибок не даёт ни в одном режиме.

`markChanges`: `before`/`after` — код статуса; `'yes'`/`'no'` для `noCoat`; число текстом или `''` для активности; у новой отметки (`old === null`) `before` — `''` у всех трёх полей, а поля со значением по умолчанию (`noCoat: false`, `activity: null`) не выдаются.

```js
  units: [{ unit, title }],
  results: { [studentId]: { units: [...], outside, preliminary, word, attendance } },     // как studentResults; {} при partial
}
```

Правила:

- `subjectId` не строка или предмета нет — `not_found`.
- Кто видит: `manager` и `reader` — любой предмет целиком; преподаватель предмета (`subject.teacherId === user.id`, роль `teacher`) — целиком; преподаватель, у которого в этом журнале есть пары с `pair.teacherId === user.id`, — `partial: true`; остальные — `forbidden`.
- `pairs` — пары предмета в датах текущего семестра (`inSemester`), все статусы, по дате, № пары, id. При `partial` — только пары этого преподавателя. `state` — `markState`; `mode` — `markMode` для этого человека: `teacher` = роль `teacher` и (`pair.teacherId === user.id` или `subject.teacherId === user.id`), `manager` — как в `viewerOf`; у проректора всегда `'none'`. `unit` — юнит темы пары или `null`; `topicName` — название темы или `''`; `number` — номер занятия (`lessonNumbers` из `core/syllabusPlan.js`, как в `pairViews`) или `''`; `first` — `firstPairId` по всем парам предмета в семестре (не только видимым); `counts` — пара проведена, не рубежная и с юнитом; `substitution` — `isSubstitution`.
- `students` — активные студенты группы предмета по `compareNames(fullName)`, затем по id; после них — с `left: true` — студенты, которых в этом списке нет, но у которых есть отметки на парах журнала или строки «Итогов юнитов» этого предмета (выключенные и переведённые). При `partial` — `left` только по видимым парам.
- `marks` — по видимым парам; из двух строк одной пары и студента берётся последняя по `markedAt`, затем по id. Полей `markedBy` и `id` в ответе нет.
- `units` — номера юнитов тем утверждённого силлабуса, по которому идёт предмет в текущей половине года (`syllabusFor`), и юнитов тем проведённых пар, по возрастанию; `title` — из таблицы «Юниты» этого силлабуса или `''`. Нет утверждённого силлабуса — `hasSyllabus: false`, `planSemester: null`, `units` — только по проведённым парам.
- `results` — `studentResults` для каждого студента из `students`; строки «Итогов юнитов» берутся по `subjectId`, `studentId` и `planSemester` предмета. При `partial` — `{}`; `units` — `[]`.
- `can.results` — `manager` или преподаватель предмета; `can.manage` — `manager`.

Список журналов (`journal.list`): `subjects: [{ subjectId, name, groupId, groupName, teacherId, teacherName, own, covers, held, unfilled, overdue }]` по `compareNames(groupName)`, `compareNames(name)`, id. `own` — человек преподаватель предмета; `covers` — у него есть пары этого предмета в семестре. `manager` и `reader` получают все предметы; только-преподаватель — те, где `own` или `covers`. `held` — проведённые пары; `unfilled` — пары со статусом `planned` и состоянием `open` или `late`; `overdue` — из них `late`. Для строки без `own` у только-преподавателя счётчики — по его парам.

Старый файл стенда: `createFileStore` на файле без ключей `attendance`, `unitResults`, `changeLog` (и с парами без `substitute`) открывается, `list` новых таблиц — `[]`, `insert` в них работает. Если нет — поправить `fileStore.js`.
