# Юнит 3 «Журнал и оценки»: план сборки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** преподаватель сам ведёт журнал «студенты × даты пар» по своему предмету и группе: статусы явки, «без халата», активность, рубежный контроль и СРС юнита; текущий контроль юнита журнал считает сам; каждое изменение отметки и оценки пишется в журнал изменений; деканат видит все журналы и незаполненные пары; студент на телефоне видит свои баллы и пропуски. QR, код, «Я на паре» и экран пары с таймером — юнит 4, поверх этого журнала.

**Architecture:** правила (схема баллов, расчёт баллов за пару и текущего контроля, срок правки, что кому можно менять) — чистые функции в `core/`. Сервер (`backend/journalData.js`, `backend/studentGrades.js`, обработчики `journal.*`, `scoring.*`, `student.grades`) читает каждую таблицу один раз за запрос, считает через `core/` и пишет пачкой; в ответ после любой записи отдаёт журнал предмета заново. Три новые таблицы: «Посещаемость», «Итоги юнитов», «Журнал изменений»; у «Пар» новая колонка «замена»; числа схемы баллов — строки в «Настройках». **Баллы за пару, текущий контроль и итоги не хранятся: они считаются при каждом чтении** из посещаемости и схемы. Сайт получает экраны: список журналов, сетка журнала, окно отметки пары, окно ячейки, окна итогов юнита, «Журнал изменений», карточка «Баллы и журнал» в «Настройках», «Оценки» студента.

**Tech Stack:** как в юните 2 с доработкой 4 — Node 24, ES-модули, `node --test`, встроенный `node:sqlite` (рабочий сервер), esbuild только для запасной сборки под Apps Script, сайт без сборки. Новых зависимостей нет.

**Spec:** `aidlc-docs/inception/design-v1.md` (раздел 6: «Пара и отметка», «Баллы за пару и текущий контроль», «Ведомость (вариант А)»; раздел 8), `aidlc-docs/inception/ТЗ.md` (разделы 2, 5, 6, 11), таблица решений `aidlc-docs/aidlc-state.md` — строки от 22.11.2026: «Порядок юнитов меняется», «Новые правила (приняты все 12)» (правила 5, 6, 7, 8, 9, 12). Где этот план расходится с `design-v1.md`, действует план (см. «Решения плана»).

**Исходное состояние:** `HEAD de389cc`, 591 тест, `npm run build:gas` собирается. План согласован владельцем 22.11.2026: все восемь вопросов `owner-summary.md` — по умолчанию; максимум юнита — 100 (ТК 40 + СРС 20 + РК 40), баллы за пары — только промежуточный шаг к текущему контролю. Сверка плана сделана (`.superpowers/sdd/plan-unit-3-zhurnal/preflight.md`), её находки внесены в этот файл. Юнит 2 с доработками 1–4 выложен; в рабочей базе — пробные данные.

## Global Constraints

Действующие правила юнита 2 (переносятся без изменений):

- `core/` и `backend/` без зависимостей из npm. Dev-зависимости проекта: `esbuild`, `xlsx`, `@fontsource-variable/inter`. Новые не добавляются.
- Сайт: без сборки, без фреймворков, ничего не загружает с чужих адресов (ни CDN, ни внешних шрифтов).
- Все обработчики сервера синхронные. `handleRequest` никогда не бросает исключение и всегда возвращает объект ответа. Ошибки — `AppError(code, { fields })` из `core/errors.js`.
- Запрос сайта: `POST`, `Content-Type: text/plain;charset=utf-8`, тело — JSON `{action, token, data}`. Своих заголовков нет.
- `passwordHash` никогда не попадает в ответ сервера. Ответы собираются по полям; строки сотрудников и студентов в ответ целиком не копируются.
- Время берётся только из `platform.now()`. `Date.now()` и `new Date()` без аргумента в `core/` и `backend/` запрещены. «Сегодня» — `localDate(platform.now())` по Бишкеку (UTC+6 круглый год). Сайт часам устройства не доверяет: «сегодня» и «сейчас» он берёт из ответа сервера.
- Дата — строка `'YYYY-MM-DD'`, время — `'HH:MM'`, дата со временем — `'YYYY-MM-DD HH:MM:SS'` (новая, `localDateTime`). Объектов `Date` в строках хранилища нет.
- В базе хранятся английские коды (`present`, `closed`), на экране они переводятся словарём.
- Обработчик читает каждую таблицу не больше одного раза за запрос (`store.list`) и пишет пачкой (`insertMany`, `updateMany`, `removeMany`). `store.get`, `store.update`, `store.remove` в цикле запрещены. На SQLite это не вопрос скорости, но код остаётся рабочим и на запасном Apps Script.
- Что попадает в сборку Apps Script, остаётся чистым: `backend/api.js`, `backend/handlers/*`, `backend/*.js` (кроме `backend/node/` и `backend/store/sqliteStore.js`), `core/*` не импортируют ничего из `backend/node/`; в них нет `node:`, `require(` и слова `process` даже в комментариях (их ищет `tests/gasBundle.test.js`).
- Роли: `admin`, `dean`, `prorector`, `teacher`, `student`. У сотрудника роли хранятся строкой через запятую; у одного человека может быть несколько ролей (`dean,teacher`).
- Любая фраза на экране идёт через ключ словаря. Наборы ключей в `ky`, `ru`, `en` одинаковые (`tests/i18n.test.js`). Названия дней и месяцев — из словаря, без `Intl`.
- Данные с сервера, от пользователя и из файлов попадают на страницу только как текст (`textContent`, помощники из `site/js/ui.js`), никогда через `innerHTML`. Это относится и к причинам правок, и к ФИО.
- Цвета — hex или rgb, без `oklch()`. Новые экраны берут цвета и размеры из переменных `site/css/app.css`. Код и картинки платного шаблона не копируются.
- Две темы, тёмная по умолчанию; каждый экран проверяется в обеих.
- Студенческие экраны — для телефона шириной 360 px: без бокового меню, текст не мельче 16 px, кнопки и ссылки-кнопки не ниже 44 px.
- Настоящих данных студентов и сотрудников в репозитории нет: ни в коде, ни в тестах, ни в отчётах, ни на скриншотах. Данные стенда вымышленные. `dev/data/` и `build/` — в `.gitignore`.
- Локальный стенд — только порт 5273. Рабочий сервер (порт 5373), папки `D:\Журнал колледжа — сервер`, `D:\Журнал колледжа — данные`, `C:\JournalBackups`, файлы `serve.local.json` и `dev/data/real.json` агенты не открывают, не запускают и не правят.
- У пары вся группа целиком (подгрупп нет — правило 5 владельца, по умолчанию). 1 пара = 2 часа.
- Сообщения коммитов на английском; в конце строка `Co-Authored-By` с той моделью, которая на самом деле писала коммит. Агент коммитит **только свои файлы по имени** (не `git add -A`) и оставляет `git status` чистым.
- `git push` и обновление рабочего сервера — только по прямой просьбе владельца.

Новые правила юнита 3:

- **Данные студентов — строго.** Студент получает в ответе только свои отметки и баллы: ни id, ни ФИО, ни отметок другого студента нет ни в одном поле. Преподаватель получает журнал только своего предмета; по чужому предмету, где он вёл отдельные пары (замена, прежний преподаватель), — только эти пары, без итогов юнитов. Проректор только смотрит. Это проверяется в тестах поиском по всему JSON ответа, а не только кодом ответа.
- **Права проверяются попыткой обойти защиту:** чужой предмет, чужая группа, чужая пара, студент другой группы в списке отметок, массив, число или строка с пробелами вместо id, будущая, отменённая и просроченная пара. Отказ — и ничего не записано: тест сравнивает снимок таблиц «Посещаемость», «Итоги юнитов», «Журнал изменений» и «Пары» до и после.
- **Журнал изменений (правило 6 владельца).** Любое изменение уже сохранённой отметки (статус, «без халата», активность), любая запись рубежного, СРС и ручного текущего контроля, «не проведена», возврат и сброс отметок пары пишут строки в «Журнал изменений» **в том же запросе** (на рабочем сервере — в той же транзакции): кто, когда, было → стало, причина, признак «после срока». Первая отметка пары в журнал изменений не пишется: кто и когда — в самой строке «Посещаемости». Таблицы «Посещаемость», «Итоги юнитов» и «Журнал изменений» пишет только `backend/journalData.js` (и `dev/seed.js` через его функции); `dir.save`, `dir.remove` и импорт этих таблиц не знают. Строки «Журнала изменений» не меняются и не удаляются никогда.
- **Всё или ничего.** Запрос с одной плохой строкой (плохой статус, чужой студент, нет причины) не записывает ничего.
- **Расчёт — при чтении.** Баллы за пару, текущий контроль, итог юнита и проценты посещаемости нигде не хранятся. Схема баллов одна на колледж (правило 8), её числа лежат в «Настройках»; силлабус её только показывает.
- **Причина правки** — текст до 300 знаков, без переводов строк по краям; хранится и показывается как текст.
- **Проверка задач (правило 12 владельца).** Проверка каждой задачи облегчённая: sonnet, короткий отчёт, пробы только на права и данные студентов. Для задач 10–15 (сервер журнала) пробы на права и «ничего не записано» обязательны всегда. После правок владельца по блоку экранов проверяется только этот блок; права и данные студентов — строго и там. Общая проверка юнита — одна, в конце, строгая, самой сильной моделью, с пробными скриптами против настоящего кода.
- **Модели.** «Логика», «Сервер», проверяющий — sonnet. «Экраны»: новые экраны (задачи 17–21, 26) — opus; небольшие окна в готовом экране, карточка, экран-таблица по образцу и тексты (задачи 22–25) — sonnet. Сверка плана и общая проверка — самая сильная модель. Модель указывается явно в каждом поручении.
- **Стенд и браузер агентов.** Перед экранными задачами стенд координатора на 5273 остановлен: агент поднимает свой (`npm run dev:reset`). Браузер для проверки — только headless Chrome с временным профилем и ключами `--disable-sync --disable-extensions`; не Edge. Процессы агент останавливает **только по своему номеру (PID)** — те, что запустил сам; никогда по имени программы или заголовку окна. Браузер и учётные записи владельца агенты не трогают.
- Вход на стенде: `admin`, `dean` (деканат и преподаватель), `prorector`, `teacher1`…`teacher3`, студенты `S1001`…; пароль — константа `DEV_PASSWORD` в `dev/seed.js`. В отчётах и скриншотах пароль не пишется.

## Review Focus

1. **Чужой журнал.** Преподаватель не читает и не правит журнал чужого предмета ни с экрана, ни прямым запросом с чужим `subjectId` или `pairId`; заменяющий видит и правит только свою пару и не получает итогов юнитов; проректор ничего не меняет; студент не вызывает ни одного действия `journal.*`. Тесты — задачи 10, 11, 12, 13, 14.
2. **Студент и чужие баллы.** `student.grades` не читает из запроса ничего: чужой `studentId`, `groupId`, `subjectId` в данных запроса не меняют ответ; в JSON ответа нет ни одного чужого id и ФИО. Тесты — задача 15.
3. **Не тот id.** Массив, число, объект, строка с пробелами вместо `pairId`, `subjectId`, `studentId`; студент другой группы или выключенный студент в списке отметок; один студент дважды — отказ, ничего не записано. Тесты — задачи 12, 13, 14.
4. **Срок правки.** До звонка пары отметки не ставятся; в срок преподаватель правит свободно; после срока незаполненную пару он заполнить не может, в заполненной делает только два изменения с причиной («не был» → «уважительная причина»; «не был» или «уважительная причина» → «отработано» с активностью); деканат и администратор меняют всё, но всегда с причиной. Граница срока — конец дня по Бишкеку (запрос в 00:30 по Бишкеку — уже следующий день). Тесты — задачи 4 и 12.
5. **Журнал изменений полон.** После каждого изменения сохранённой отметки, рубежного, СРС, ручного текущего контроля, «не проведена», возврата и сброса в «Журнале изменений» есть строка с верными «было», «стало», автором и причиной; при отказе строк нет; повтор того же значения строк не создаёт. Тесты — задачи 12, 13, 14.
6. **Расчёт.** Первая пара предмета — только явка; рубежная пара в текущий контроль не входит; «уважительная причина» и пара без отметки не входят в расчёт; «отработано» даёт явку и активность; округление половины вверх; ручной текущий контроль перекрывает расчётный и снимается; пары без темы — вне юнитов; итог юнита появляется только при выставленных СРС и рубежном; после уменьшения максимумов схемы выставленные рубежный, СРС и ручной текущий считаются не больше нового максимума (итог юнита не бывает больше 100). Числа — из раздела «Правила расчёта». Тесты — задачи 3, 10, 15.
7. **Схема баллов.** Сумма «текущий + СРС + рубежный» не равна 100, пороги не по возрастанию, не числа — ошибка у поля, ничего не записано; испорченные строки «Настроек» дают схему по умолчанию; сохранение настроек семестра не трогает числа схемы и наоборот; после смены чисел журнал пересчитан. Тесты — задачи 1, 7 и 10.
8. **Проведённая пара и темы.** Сохранение отметок делает пару проведённой (`closed`), её тема закрепляется; проведённая пара без темы получает тему при следующей раскладке; «не проведена» отдаёт тему следующей непроведённой паре; сброс отметок возвращает пару в расписание. Прежние защиты силлабуса (тему проведённой пары нельзя убрать) работают на парах, проведённых через журнал; проведённая пара без темы из прошлого семестра занятий нового семестра не забирает. Тесты — задачи 5, 12, 14.
9. **Замена и смена преподавателя.** Прошедшие пары прежнего преподавателя не помечены «Замена»; разовая замена помечена и после того, как пара проведена и преподаватель предмета сменился; отметки на паре замены ставит и заменяющий, и преподаватель предмета. Тесты — задачи 5, 8, 12.
10. **Курс и семестр (правило 7).** «2 курс 1 семестр» в файле читается как семестр 3 с замечанием; титул, где курс не сходится с семестром по плану, не отправляется и не утверждается; группа другого курса — предупреждение при отправке и утверждении; на экране у этих ошибок свой текст, а не «не выбран семестр». Тесты — задачи 6, 9 и 25.
11. **Запрет удаления.** Студента с отметками или итогами, сотрудника, который ставил отметки или записан в журнале изменений, предмет с итогами юнитов удалить нельзя (`in_use`); пары с отметками не удаляются пересозданием расписания. Тесты — задача 8.
12. **Выбывший студент.** Студент, переведённый в другую группу или выключенный, не пропадает из журнала молча: его прежние отметки видны строкой «выбыл», в расчёты других студентов он не входит. Тесты — задача 10.
13. **Одно чтение каждой таблицы.** `journal.get`, `journal.savePair`, `journal.saveResults`, `student.grades` читают каждую таблицу один раз и пишут не больше одной пачки каждого вида на таблицу. Тесты со шпионом — задачи 10, 11, 12, 13, 15.
14. **Алфавит.** Список студентов журнала стоит по алфавиту с Ё после Е, Ң после Н, Ө после О, Ү после У, без учёта регистра. Тесты — задачи 3 и 10.
15. **Экраны.** Сетка на 22 студента и 40 пар прокручивается внутри таблицы, первая колонка на месте; двойное нажатие «Сохранить» не шлёт два запроса; ответ, пришедший после ухода со страницы, ничего не рисует; несохранённые отметки и уход со страницы; текст причины с `<script>` и `=СУММ()` остаётся текстом; студент на телефоне 360 px без горизонтальной прокрутки страницы. Проверка на стенде — задачи 17–26.

Проверяющий задач 10–15 отдельно убеждается: каждая проверка «ничего не записано», «каждая таблица один раз», «в ответе нет чужого студента» написана настоящим `assert` по данным, а не комментарием и не проверкой кода ответа.

## Правила расчёта (с числами)

Схема по умолчанию: явка **20**, активность **0–10**, текущий контроль **40**, СРС **20**, рубежный **40**, зачётный минимум **24**, пороги **60 / 76 / 90**.

Баллы студента за одну проведённую пару (`closed`, в юните 4 ещё `running`):

| Случай | Набрано | Возможно | Входит в текущий контроль |
| --- | --- | --- | --- |
| был, опоздал, отработано; обычная пара | 20 + активность (пусто = 0) | 30 | да |
| не был; обычная пара | 0 | 30 | да |
| первая пара предмета: был, опоздал, отработано | 20 (активности нет) | 20 | да |
| первая пара предмета: не был | 0 | 20 | да |
| уважительная причина | — | — | нет, пока не станет «отработано» |
| у студента нет отметки на этой паре | — | — | нет |
| рубежная пара (тип занятия `control`) | — | — | нет: явка отмечается, баллов нет |
| пара не проведена, отменена, не заполнена | — | — | нет |

- **Первая пара предмета** — самая ранняя (дата, № пары, id) пара предмета в датах текущего семестра со статусом `planned`, `running` или `closed`. Отменённая и «не проведена» первой не считаются.
- **Текущий контроль юнита** = сумма набранного / сумма возможного × 40 по парам этого юнита, округление до целого (`Math.round`: половина вверх). Возможного нет — текущего контроля нет (пусто). Баллы за пары («72 из 110») — только промежуточный шаг: текущий контроль всегда из 40, сколько бы пар ни было в юните, а итог юнита — из 100.
- Пары без темы (без юнита) считаются так же, но показываются отдельно («вне юнитов») и в юниты не входят.
- **Ручной текущий контроль** перекрывает расчётный; расчётный показывается рядом.
- **Итог юнита** = текущий + СРС + рубежный; пусто, пока не выставлены и СРС, и рубежный (и есть текущий).
- **Оценка словом:** до 59 — `fail` (неуд.), 60–75 — `fair` (удовл.), 76–89 — `good` (хорошо), 90–100 — `excellent` (отлично).
- **Предварительно по предмету** — среднее итогов юнитов, у которых итог есть, округление до целого; ни одного — пусто.
- **Ниже минимума:** текущий < 24 или рубежный < 24 (когда значение есть).
- **Посещаемость:** `marked` — число проведённых пар, где у студента есть отметка (рубежные входят); `attended` — был + опоздал + отработано; процент = `attended / marked × 100`, округление до целого; `marked = 0` — пусто.
- **Схему уменьшили.** Сохранённые активность, рубежный, СРС и ручной текущий контроль больше нынешнего максимума считаются как максимум (значения в базе не меняются). Пример: рубежный 40 выставлен при максимуме 40, потом схему сменили на «текущий 50, СРС 20, рубежный 30» — рубежный читается как 30, и итог юнита не превышает 100.

Пример (юнит 1, обычные пары, кроме первой):

| Пара | Отметка | Набрано / возможно |
| --- | --- | --- |
| 1 (первая пара предмета) | был | 20 / 20 |
| 2 | был, активность 7 | 27 / 30 |
| 3 | опоздал, активность 5 | 25 / 30 |
| 4 | не был | 0 / 30 |
| 5 | уважительная причина | не входит |

Набрано 72 из 110 → 72 / 110 × 40 = 26,18 → **текущий контроль 26**. Студент отработал пару 5 с активностью 8 (28 / 30): 100 из 140 → 28,57 → **29**. СРС 16, рубежный 30 → **итог юнита 75, «удовлетворительно»**; при рубежном 31 — 76, «хорошо».

  minimum: 24, fair: 60, good: 76, excellent: 90, editDays: 3 });
export const SCHEME_FIELDS = ['attendance', 'activity', 'current', 'self', 'control', 'minimum', 'fair', 'good', 'excellent', 'editDays'];
export const SCHEME_KEYS = { attendance: 'scoreAttendance', activity: 'scoreActivity', current: 'scoreCurrent', self: 'scoreSelf',
  control: 'scoreControl', minimum: 'scoreMinimum', fair: 'scoreFair', good: 'scoreGood', excellent: 'scoreExcellent', editDays: 'journalEditDays' };

Правила `validateScheme`:

- Каждое поле — целое число или строка из цифр (пробелы по краям убираются); иначе `{ field, code: 'bad_value' }`. В `value` — числа.
- Границы: `attendance` 1–100; `activity` 0–100; `current` 1–100; `self` 0–100; `control` 0–100; `minimum` 0–100; `fair`, `good`, `excellent` 1–100; `editDays` 0–60. Вне границ — `bad_value`.
- `current + self + control` должно быть 100 — иначе `{ field: 'control', code: 'sum' }` (проверяется, если все три поля верны).
- `minimum` от 0 до меньшего из `current` и `control` — иначе `{ field: 'minimum', code: 'too_big' }`.
- `fair < good < excellent` — иначе `{ field: 'good', code: 'order' }` или `{ field: 'excellent', code: 'order' }` у первого нарушившего поля.
- Ошибки идут в порядке `SCHEME_FIELDS`, не больше одной на поле.

`readScheme`: берёт первую строку каждого ключа `SCHEME_KEYS`; нет строки или значение не целое — значение по умолчанию; если собранная схема не проходит `validateScheme` — возвращается копия `DEFAULT_SCHEME` целиком. Чужие ключи «Настроек» не мешают. Файл попадёт в сборку Apps Script: слова `process` в нём нет.

// -> 'cancelled' | 'missed' | 'future' | 'open' | 'late'
//    cancelled, missed — по статусу пары; future — день пары ещё не настал или настал, но now.time < pair.startTime;
//    open — now.date <= addDays(pair.date, scheme.editDays); иначе late

export function markMode({ state, held, teacher, manager });
// held: пара проведена (статус в FIXED_STATUSES); teacher: человек ведёт эту пару или предмет; manager: администратор или деканат
// -> 'free' (любая правка без причины) | 'reason' (любая правка, причина обязательна) | 'limited' (два изменения с причиной) | 'none'

Правила `checkMark`:

- `status` не из `ATTENDANCE_STATUSES` — `{ field: 'status', code: 'bad_value' }`.
- `activity` не `null`, когда статус не из `ATTENDED_STATUSES`, или пара первая (`pair.first`), или рубежная (`lessonType === 'control'`) — `{ field: 'activity', code: 'not_allowed' }`; вне 0…`scheme.activity` — `bad_value`.
- Режим `limited`: разрешено только `old.status === 'absent'` → `excused` (без активности) и `old.status` из `absent`, `excused` → `madeup` (активность по правилам выше); `noCoat` не меняется. Всё остальное, что меняет отметку, и `old === null` — `{ field: 'status', code: 'locked' }`.
- Режим `none` — `{ field: 'status', code: 'locked' }` при любом изменении.
- Отметка без изменений ошибок не даёт ни в одном режиме.

`markChanges`: `before`/`after` — код статуса; `'yes'`/`'no'` для `noCoat`; число текстом или `''` для активности; у новой отметки (`old === null`) `before` — `''` у всех трёх полей, а поля со значением по умолчанию (`noCoat: false`, `activity: null`) не выдаются.

Журнал:

```js

  today: '2026-09-08', now: '08:05',

```

Правила:

- `subjectId` не строка или предмета нет — `not_found`.
- Кто видит: `manager` и `reader` — любой предмет целиком; преподаватель предмета (`subject.teacherId === user.id`, роль `teacher`) — целиком; преподаватель, у которого в этом журнале есть пары с `pair.teacherId === user.id`, — `partial: true`; остальные — `forbidden`.
- `pairs` — пары предмета в датах текущего семестра (`inSemester`), все статусы, по дате, № пары, id. При `partial` — только пары этого преподавателя. `state` — `markState`; `mode` — `markMode` для этого человека: `teacher` = роль `teacher` и (`pair.teacherId === user.id` или `subject.teacherId === user.id`), `manager` — как в `viewerOf`; у проректора всегда `'none'`. `unit` — юнит темы пары или `null`; `topicName` — название темы или `''`; `number` — номер занятия (`lessonNumbers` из `core/syllabusPlan.js`, как в `pairViews`) или `''`; `first` — `firstPairId` по всем парам предмета в семестре (не только видимым); `counts` — пара проведена, не рубежная и с юнитом; `substitution` — `isSubstitution`.
- `students` — активные студенты группы предмета по `compareNames(fullName)`, затем по id; после них — с `left: true` — студенты, которых в этом списке нет, но у которых есть отметки на парах журнала или строки «Итогов юнитов» этого предмета (выключенные и переведённые). При `partial` — `left` только по видимым парам.
- `marks` — по видимым парам; из двух строк одной пары и студента берётся последняя по `markedAt`, затем по id. Полей `markedBy` и `id` в ответе нет.
- `units` — номера юнитов тем утверждённого силлабуса, по которому идёт предмет в текущей половине года (`syllabusFor`), и юнитов тем проведённых пар, по возрастанию; `title` — из таблицы «Юниты» этого силлабуса или `''`. Нет утверждённого силлабуса — `hasSyllabus: false`, `planSemester: null`, `units` — только по проведённым парам.
- `results` — `studentResults` для каждого студента из `students`; строки «Итогов юнитов» берутся по `subjectId`, `studentId` и `planSemester` предмета. При `partial` — `{}`; `units` — `[]`.
- `can.results` — `manager` или преподаватель предмета; `can.manage` — `manager`.

Старый файл стенда: `createFileStore` на файле без ключей `attendance`, `unitResults`, `changeLog` (и с парами без `substitute`) открывается, `list` новых таблиц — `[]`, `insert` в них работает. Это только тест: код хранилища уже так работает.
