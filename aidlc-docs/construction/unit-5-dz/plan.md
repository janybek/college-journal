# Юнит 5 «ДЗ и СРС»: план сборки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** преподаватель выдаёт задание ДЗ или СРС — на экране «Задания» или кнопкой на этапе «Итог» идущей пары (тема и юнит пары подставляются сами); студент с телефона сдаёт текст и до 5 файлов (фото уменьшается на телефоне); преподаватель открывает файлы, ставит баллы и комментарий или возвращает на доработку; балл СРС юнита журнал считает сам по заданиям СРС этого юнита (набрано / максимум × 20), а в юните без заданий СРС преподаватель вводит его числом, как в юните 3; ДЗ оценивается и видно студенту, но в итог не входит; деканат и проректор видят всё, но не оценивают.

**Architecture:** правила (проверка задания, состояние работы, балл СРС по заданиям, проверка оценки, имя и вид файла по содержимому) — чистые функции `core/work.js` и `core/files.js`. Три новые таблицы: «Задания», «Сдачи» (одна строка на попытку сдачи, текущая — с наибольшим номером), «Файлы» (только описание файла; сам файл лежит на диске в папке данных под случайным именем). Файлы ходят тем же единственным запросом сайта `POST {action, token, data}`: загрузка — один файл на запрос, base64 в JSON (`work.upload`), просмотр — `work.file` с проверкой прав, base64 в ответе; сайт сам собирает `Blob` с типом из своего списка. Доступ к диску — через объект `ctx.files` («ящик файлов»): на рабочем сервере и стенде он пишет в папку, в тестах — в память; в запасной сборке Apps Script его нет (`files_unavailable`). Удаляет файлы с диска только уборка на Node (при запуске и после ежедневной копии), никогда — запрос. Ежедневная копия дописывает новые файлы в `C:\JournalBackups\files`. Балл СРС считается при чтении журнала (как весь юнит 3) и в итог юнита идёт, когда по всем заданиям СРС юнита решено.

**Tech Stack:** как в юнитах 3–4 — Node 24, ES-модули, `node --test`, встроенный `node:sqlite`, esbuild только для запасной сборки Apps Script, сайт без сборки; `<canvas>` для уменьшения фото, `XMLHttpRequest` для полосы загрузки. Новых зависимостей нет.

**Spec:** `aidlc-docs/inception/design-v1.md` (раздел 6 «ДЗ и СРС», «Ведомость (вариант А)», раздел 7 — кабинет студента «Оценки · ДЗ · Пропуски»), `aidlc-docs/inception/ТЗ.md` (ДЗ и СРС, кабинет студента, таблицы «Задания» и «Сдачи»), таблица решений `aidlc-docs/aidlc-state.md` — 20.11.2026 «ДЗ … в итог не входит», 22.11.2026 «Новые правила (приняты все 12)» и «Порядок юнитов меняется», 22.11.2026 «План юнита 3 … СРС за юнит одним числом», **23.11.2026 «Юнит 5 „ДЗ и СРС“ — вопросы до плана»**; план юнита 3 `aidlc-docs/construction/unit-3-zhurnal/plan.md` (модель журнала, «Правила расчёта», журнал изменений — действуют без изменений, кроме СРС юнита с заданиями). `design-v1.md` писался под Google («файл уходит в папку на Google Диске»): сервер теперь Node + SQLite на компьютере владельца за Tailscale Funnel, файлы — в папке данных рядом с базой. Где `design-v1.md` расходится с таблицей решений или с этим планом, действуют они.

**Исходное состояние:** `HEAD adc6e6b` (после `63fa74c` только документы), **787 тестов** (`npm test` 23.11.2026), `npm run build:gas` собирается. Юниты 1–4 приняты и выложены (сервер и сайт `47a5089`). Ответы владельца до плана (23.11.2026, все по умолчанию): с телефона — текст и до 5 файлов по 10 МБ (фото, PDF, Word, Excel, PowerPoint), фото уменьшается на телефоне; СРС юнита = по заданиям СРС юнита (набрано / максимум × 20), без заданий — число рукой, как в юните 3; задание выдаётся на этапе «Итог» идущей пары и на экране «Задания»; деканат и проректор видят всё (задания, работы с файлами, баллы, комментарии), но не оценивают. Экраны — **три блока с остановкой после каждого** (как в юнитах 3–4): блок 1 — задачи 9–10 (преподаватель), блок 2 — задача 11 (студент), блок 3 — задача 12 (деканат, журнал, «Оценки», «Журнал изменений»). После блока 3 — одна строгая общая проверка (opus), одна волна исправлений, повторная проверка, выкладка (задача 13).

## Global Constraints

Действующие правила юнитов 2–4 (переносятся без изменений):

- `core/` и `backend/` без зависимостей из npm. Dev-зависимости проекта: `esbuild`, `xlsx`, `@fontsource-variable/inter`. Новые не добавляются.
- Сайт: без сборки, без фреймворков, ничего не загружает с чужих адресов (ни CDN, ни внешних шрифтов).
- Все обработчики сервера синхронные. `handleRequest` никогда не бросает исключение и всегда возвращает объект ответа. Ошибки — `AppError(code, { fields })` из `core/errors.js`.
- Запрос сайта: `POST`, `Content-Type: text/plain;charset=utf-8`, тело — JSON `{action, token, data}`. Своих заголовков нет.
- Исключение — `work.upload` с полосой хода: `XMLHttpRequest` с обработчиком `xhr.upload.onprogress` по стандарту всегда делает предварительный запрос `OPTIONS` (CORS preflight), даже при `text/plain`. Рабочий сервер на него отвечает (задача 4). Стенду не нужно: сайт и `/api` у него на одном адресе.
- `passwordHash` никогда не попадает в ответ сервера. Ответы собираются по полям; строки сотрудников и студентов в ответ целиком не копируются.
- Время берётся только из `platform.now()`. `Date.now()` и `new Date()` без аргумента в `core/` и `backend/` запрещены. «Сегодня» — `localDate(platform.now())` по Бишкеку (UTC+6 круглый год). Сайт часам устройства не доверяет: «сегодня» и «сейчас» он берёт из ответа сервера (срок «просрочено» и «осталось» — тоже).
- Дата — строка `'YYYY-MM-DD'`, время — `'HH:MM'`, дата со временем — `'YYYY-MM-DD HH:MM:SS'` (`localDateTime`). Объектов `Date` в строках хранилища нет.
- В базе хранятся английские коды (`srs`, `checked`, `pdf`), на экране они переводятся словарём.
- Обработчик читает каждую таблицу не больше одного раза за запрос (`store.list`) и пишет пачкой (`insertMany`, `updateMany`, `removeMany`). `store.get`, `store.update`, `store.remove` в цикле запрещены.
- Что попадает в сборку Apps Script, остаётся чистым: `backend/api.js`, `backend/handlers/*`, `backend/*.js` (кроме `backend/node/` и `backend/store/sqliteStore.js`), `core/*` не импортируют ничего из `backend/node/`; в них нет `node:`, `require(`, `Buffer` и слова `process` даже в комментариях (их ищет `tests/gasBundle.test.js`).
- Роли: `admin`, `dean`, `prorector`, `teacher`, `student`. У сотрудника роли хранятся строкой через запятую; у одного человека может быть несколько ролей (`dean,teacher`).
- Любая фраза на экране идёт через ключ словаря. Наборы ключей в `ky`, `ru`, `en` одинаковые (`tests/i18n.test.js`). Названия дней и месяцев — из словаря, без `Intl`.
- Данные с сервера, от пользователя и из файлов попадают на страницу только как текст (`textContent`, помощники из `site/js/ui.js`), никогда через `innerHTML`. Это относится к тексту работы, комментарию, названию задания и **имени файла**.
- Цвета — hex или rgb, без `oklch()`. Новые экраны берут цвета и размеры из переменных `site/css/app.css`. Код и картинки платного шаблона не копируются.
- Две темы, тёмная по умолчанию; каждый экран проверяется в обеих. Исключение — экран пары (в том числе окно задания на этапе «Итог»): он всегда светлый.
- Студенческие экраны — для телефона шириной 360 px: без бокового меню, текст не мельче 16 px, кнопки и ссылки-кнопки не ниже 44 px.
- Настоящих данных студентов и сотрудников в репозитории нет: ни в коде, ни в тестах, ни в отчётах, ни на скриншотах. `dev/data/` и `build/` — в `.gitignore`.
- Локальный стенд — только порт 5273. Рабочий сервер (порт 5373), папки `D:\Журнал колледжа — сервер`, `D:\Журнал колледжа — данные`, `C:\JournalBackups`, файлы `serve.local.json` и `dev/data/real.json`, папка `dev/data/real-files/` агенты не открывают, не запускают и не правят.
- У пары вся группа целиком (подгрупп нет). 1 пара = 2 часа.
- Сообщения коммитов на английском; в конце строка `Co-Authored-By` с той моделью, которая на самом деле писала коммит. Агент коммитит **только свои файлы по имени** (не `git add -A`) и оставляет `git status` чистым.
- `git push` и обновление рабочего сервера — только по прямой просьбе владельца.
- **Данные студентов — строго.** Студент получает в ответе только своё: ни id, ни ФИО, ни работ, ни файлов, ни баллов другого студента, ни числа сдавших. Проверяется поиском по всему JSON ответа, а не только кодом ответа.
- **Права проверяются попыткой обойти защиту.** Отказ — и ничего не записано: тест сравнивает снимок таблиц до и после (и список имён в ящике файлов).
- **Журнал изменений** (правило 6 владельца) пишется в том же запросе; строки не меняются и не удаляются никогда.
- **Всё или ничего.** Запрос с одной плохой строкой не записывает ничего.
- Причина правки — текст до 300 знаков (`checkReason` из `core/journal.js`), хранится и показывается как текст.
- Стенд и браузер агентов: перед экранными задачами стенд координатора на 5273 остановлен, агент поднимает свой (`npm run dev:reset`). Браузер для проверки — только headless Chrome с временным профилем и ключами `--disable-sync --disable-extensions`; не Edge. Процессы агент останавливает **только по своему номеру (PID)** — те, что запустил сам; никогда по имени программы или заголовку окна. Браузер и учётные записи владельца агенты не трогают.
- Вход на стенде: `admin`, `dean` (деканат и преподаватель), `prorector`, `teacher1`…`teacher3`, студенты `S1001`…; пароль — константа `DEV_PASSWORD` в `dev/seed.js`. В отчётах и скриншотах пароль не пишется.

Новые правила юнита 5:

- **Файлы — не в базе и не в репозитории.** Файл лежит на диске: рабочий сервер — `<dataDir>\files\`, стенд — `dev/data/files/` (с настоящими данными — `dev/data/real-files/`). Имя на диске — 32 случайных hex-знака (`platform.randomHex(16)`) и `.bin`; путь строится только из такого имени после проверки `/^[0-9a-f]{32}\.bin$/`. Имя, которое дал студент, хранится только текстом в «Файлах» и никогда не попадает в путь.
- **Файлы ходят только через `/api`.** Загрузка — `work.upload`, один файл на запрос, содержимое base64 в `data.data`; просмотр — `work.file`, base64 в ответе, после проверки прав. Нет адресов вида `GET /files/…`, нет токена в адресе, нет общедоступных ссылок. Сайт собирает `Blob` с типом из своего списка по `kind` (не по имени и не из ответа): картинка — `<img src="blob:…">`, PDF — открывается в новой вкладке, остальное — скачивается. HTML и SVG не принимаются вовсе, поэтому показать их на странице нечем.
- **Вид файла — по содержимому.** Принимаются ровно 9 видов: `jpg`, `png`, `pdf`, `docx`, `xlsx`, `pptx`, `doc`, `xls`, `ppt`. Расширение имени должно совпасть с видом по первым байтам (`sniffKind`); файлы Office с макросами (`vbaProject.bin`, `_VBA_PROJECT`) не принимаются. Всё остальное — отказ.
- **Пределы** (постоянные в `core/files.js`, не в «Настройках»): файл до **10 МиБ** (10 485 760 байт); **до 5 файлов** в одной сдаче; загрузок студента за день по Бишкеку — не больше **60** и не больше **200 МиБ**; текст работы — до 5000 знаков, комментарий преподавателя — до 2000, название задания — до 200, описание — до 5000, имя файла — до 120.
- **Диск чистит только уборка.** Ни один запрос не удаляет файлы с диска (отказ откатывает запись в базе, а файл уже записан — его подберёт уборка). `sweepFiles` (Node, задача 4) удаляет строки незакреплённых и убранных файлов старше 24 часов и файлы на диске без живой строки старше 1 часа. Таймеров в `core/` и `backend/` (кроме `backend/node/`) нет.
- **Таблицы «Задания», «Сдачи», «Файлы»** пишут только `backend/workData.js`, `backend/workStudent.js`, `backend/workFiles.js`, `backend/workGrade.js` и `dev/seed.js` через их правила; `dir.*` и импорт этих таблиц не знают.
- **Кто что может.** Задания создаёт, меняет, удаляет и оценивает только преподаватель предмета — `subject.teacherId` сейчас (после смены преподавателя — новый; заменяющий на паре — нет). Деканат, проректор и администратор читают всё (задания, сдачи, файлы, баллы, комментарии) и не оценивают. Студент видит задания предметов **своей нынешней** группы и только свои сдачи и файлы.
- **Баллы и журнал изменений.** Каждое изменение баллов и статуса проверки пишет строку «Журнала изменений» (`entity: 'work'`) в том же запросе. Первая оценка — без причины; изменение уже поставленных баллов и возврат проверенной работы — с причиной (вопрос 3, по умолчанию). Смена `maxPoints` или `dueAt` у задания с попытками тоже пишет строку (без причины; вопрос 8).
- **Запасной Apps Script:** в нём нет ящика файлов — `work.upload`, `work.dropFile`, `work.file` отвечают `files_unavailable`; задания, сдача только текстом, проверка и СРС по заданиям работают. `npm run build:gas` собирается; живьём на Apps Script юнит 5 не проверяется.
- **Юниты 3–4 не меняются.** Все прежние тесты остаются зелёными без правок, кроме прямо названных в задачах 3 и 5 проверок списков таблиц, колонок и прав. СРС юнита без заданий СРС — как в юните 3.
- **Проверка задач** (правило 12 и правило экономии от 22.11.2026): после каждой задачи 1–8 — облегчённая проверка (sonnet, короткий отчёт); пробы на права, данные студентов и файлы — **строгие** для задач 1, 3, 4, 5, 6, 7 (обход, снимок таблиц, поиск в JSON, подложные файлы). Экранные задачи: проверка ИИ — только задачи 10, 11, 12 (оценки, данные студентов, файлы); задачу 9 владелец принимает блоком. Общая проверка юнита — одна, в конце, строгая, opus, с пробными скриптами против настоящего кода.
- **Модели.** «Логика», «Сервер», «Экраны», проверяющий — sonnet; сверка плана и общая проверка — opus. Модель указывается явно в каждом поручении.

## Review Focus

1. **Чужой студент.** Студент другой группы, студент, переведённый после сдачи, студент с `assignmentId`/`fileId` массивом, числом, строкой с пробелами — `work.get`, `work.upload`, `work.submit`, `work.dropFile`, `work.file` отказывают; ничего не записано (снимок «Заданий», «Сдач», «Файлов», «Журнала изменений», «Итогов юнитов» и имён ящика). Студент не читает чужой файл по id, даже зная его. Тесты — задачи 6, 7.
2. **Чужой преподаватель и контора.** `teacher2` на предмете `teacher1`; заменяющий `teacher3`; прежний преподаватель после смены преподавателя предмета; деканат (`dean,teacher`) на чужом предмете; проректор и администратор — `work.save`, `work.remove`, `work.grade` — `forbidden`, ничего не записано; читать (`work.get`, `work.file`) деканат, проректор и администратор могут. Тесты — задачи 5, 7.
3. **Подложный файл.** `.exe`, переименованный в `.jpg`; SVG и HTML со `<script>` под именем `.png`/`.pdf`; ZIP без `word/document.xml` под именем `.docx`; `.docx` с `vbaProject.bin`; `.doc` с `_VBA_PROJECT`; расширение не совпадает с содержимым; 10 МиБ + 1 байт; пустой файл; base64 с пробелом или переводом строки; имя `..\..\x/evil.pdf`, имя с NUL, с символами смены направления текста, 300 знаков. Отказ или чистое имя, на диске — только случайное имя. Тесты — задачи 1, 6.
4. **Много файлов.** Шестой файл в одной сдаче; чужой `fileId` в `work.submit` (другого студента, другого задания, уже закреплённый, убранный, старше 24 часов); 61-я загрузка за день и 200 МиБ за день — отказ, ничего не записано. Тесты — задача 6.
5. **Удалённое задание и закрытая работа.** Задание со сдачами не удаляется (`in_use`); после удаления задания без сдач его загрузки и сдача — `not_found`, незакреплённые файлы убраны; проверенную работу студент не пересдаёт (`already_checked`). Тесты — задачи 5, 6.
6. **Баллы.** Больше максимума, меньше нуля, дробь, строка, баллы при возврате, возврат без комментария, возврат без сдачи, повтор тех же значений (ничего не пишется), изменение баллов без причины — отказ; оценка на попытку, которой преподаватель не видел (`attempt_changed`, ничего не записано); смена `maxPoints`/`dueAt` у задания с попытками — строка журнала без причины; каждая запись — строки «Журнала изменений» с верными «было», «стало», автором, заданием и причиной. Тесты — задача 7.
7. **СРС по заданиям.** Числа раздела «Правила расчёта»; юнит без заданий СРС — как в юните 3; ручной СРС на юните с заданиями — `self_by_work`, сохранённое число не действует; итог юнита — только когда по всем заданиям СРС решено; уменьшение схемы; ДЗ в итог не входит; студент в «Оценках» видит то же число, что преподаватель в журнале. Тесты — задачи 2, 7.
8. **Просмотр файла безопасен.** `work.file` отдаёт только `kind` из 9 видов; сайт берёт тип `Blob` из своего списка; имя файла показывается текстом; HTML, SVG и неизвестный вид не открываются на странице. Тесты — задачи 6, 10.
9. **Диск и копии.** Отказ после записи файла на диск оставляет «сироту», которую убирает уборка; уборка не трогает файлы живых строк и свежие файлы; копия дописывает только новые файлы; восстановление копии возвращает недостающие файлы; мало места — файл тревоги на Рабочем столе. Тесты — задача 4.
10. **Одно чтение каждой таблицы.** `journal.get`, `student.grades`, `work.*` читают каждую таблицу один раз; прежние проверки «каждая из `JOURNAL_TABLES` — один раз» остаются верными с новыми таблицами. Тесты — задачи 5, 6, 7.
11. **Экраны.** Студент на 360 px без горизонтальной прокрутки; двойное нажатие «Сдать» шлёт одну сдачу; загрузка показывает ход и даёт «Повторить» без потери остальных файлов; фото уменьшено до 1600 px по длинной стороне; ответ, пришедший после ухода со страницы, ничего не рисует; несохранённая оценка и уход. Проверка на стенде — задачи 9–12.

Проверяющий задач 5–7 отдельно убеждается: каждая проверка «ничего не записано», «в ответе нет чужого», «каждая таблица один раз» написана настоящим `assert` по данным, а не комментарием.

## Чего в юните 5 нет

- **Зачётной недели, государственных экзаменов, объявлений, «Ведомостей», закрытия юнита, заявок на исправление** — юнит 6. Пока юнит не закрывается, преподаватель может менять баллы заданий в любое время (с причиной, если меняет поставленные).

- Прикреплённого файла силлабуса и необязательных вкладок 4–8 (правило 4 от 22.11.2026) — вопрос 7: по умолчанию отдельная небольшая задача сразу после юнита 5 на том же ящике файлов.
- Продления срока одному студенту, показа задания «с даты», копирования задания в другую группу, банка заданий, группового задания.
- Оценки ДЗ в итог (решение 20.11.2026), «отработки» пропуска через задание.
- Просмотра Word, Excel, PowerPoint внутри сайта (они скачиваются), сжатия PDF и документов, распознавания текста.
- Чисел пределов в «Настройках»: 10 МиБ, 5 файлов, 60 загрузок, 200 МиБ, 24 часа — постоянные в `core/files.js`.
- Удаления файлов сданных работ (хранятся, пока есть база; архив — позже).
- ИИ (проверка работ ИИ — «в самую последнюю очередь», правило 11).

## Правила расчёта (с числами)

Схема по умолчанию: СРС **20**. `selfByWork` (задача 2) по одному юниту и одному студенту, по заданиям СРС этого предмета с `planSemester` нынешнего силлабуса и этим `unit`:

| Текущая попытка студента | Набрано | Максимум | Решено |
| --- | --- | --- | --- |
| `checked` (и «на бумаге») | её баллы | максимум задания | да |
| нет попытки, срок прошёл (`now > dueAt`) | 0 | максимум задания | да |
| нет попытки, срок не прошёл | 0 | максимум задания | нет |
| `submitted` или `returned` | 0 | максимум задания | нет |

`value = Math.round(набрано × СРС / максимум)` (половина вверх); `pending` — число нерешённых. В итог юнита идёт `value` только при `pending = 0`; иначе СРС показан «предварительно», итога юнита нет. В юните без заданий СРС — ручной СРС юнита 3 (`unitResults.self`).

Пример: юнит 2, задания СРС **А** (максимум 10, срок 20.09 23:59) и **Б** (максимум 20, срок 27.09 23:59); ДЗ **В** (максимум 5) не считается.

| Когда | Студент | А | Б | Набрано / максимум | СРС |
| --- | --- | --- | --- | --- | --- |
| 24.09 | a1 | проверено 8 | сдано, ждёт | 8 / 30 | 5 (5,33) предварительно |
| 24.09 | a2 | проверено 10 (сдано 21.09 — «с опозданием») | нет, срок не прошёл | 10 / 30 | 7 (6,67) предварительно |
| 24.09 | a3 | нет, срок прошёл → 0 | возвращено | 0 / 30 | 0 предварительно |
| 28.09 | a1 | 8 | проверено 15 | 23 / 30 | **15** (15,33), выставлен |
| 28.09 | a2 | 10 | нет, срок прошёл → 0 | 10 / 30 | **7** (6,67), выставлен |
| 28.09 | a3 | 0 | проверено 12 | 12 / 30 | **8**, выставлен |

- Половина: 3 из 40 → 1,5 → **2**.
- Схему сменили на «текущий 40, СРС 30, рубежный 30»: a1 → 23 / 30 × 30 = **23**.
- Итог юнита a1 на 28.09 при текущем 26 и рубежном 30: 26 + 15 + 30 = **71**, «удовлетворительно».
- Для юнита 2 раньше вручную стоял СРС 16 — пока у юнита есть задания СРС, он не действует (в журнале показано «введено вручную: 16 — не действует»); если оба задания удалить (это можно только без сдач), снова действует 16.
- Задание СРС юнита, которого нет в нынешнем силлабусе (силлабус сменили), в расчёт не входит; в списке заданий оно видно.

Правила `checkAssignment` (код ошибки в `{ field, code }`):

- `kind` не из `['hw', 'srs']` — `kind/bad_value`.
- `unit`: у `srs` — целое из `units`, иначе `unit/bad_value`; у `hw` — `null`/нет → `null`, иначе целое из `units`.
- `topicId`: нет или `''` → `''`; не найден в `topics` — `topicId/bad_ref`; найден, `unit` задан и не равен `topic.unit` — `topicId/bad_ref`; `unit` не задан (ДЗ) — `unit` берётся из темы.
- `title`: после обрезки пробелов пусто — `title/empty`; длиннее 200 — `title/too_long`. `description`: не строка → `''`; длиннее 5000 — `description/too_long`.
- `dueDate` не `isDate` или `dueTime` не `isTime` — `due/bad_value`; `dueAt = dueDate + ' ' + dueTime + ':00'`; если задание новое или `dueAt !== old.dueAt`: `parseLocalDateTime(dueAt) <= nowMs` — `due/due_past`; больше `nowMs + WORK.farMs` — `due/too_far`.
- `maxPoints` не целое 1…100 — `maxPoints/bad_value`; `maxGiven !== null && maxPoints < maxGiven` — `maxPoints/below_points`.
- `locked` и `kind`, `unit` или `topicId` отличаются от `old` — `kind|unit|topicId/locked`.
- При изменении (`old` задан), если `kind`, `unit` и `topicId` равны `old`, `unit` и `topicId` по `units`/`topics` не проверяются: задание остаётся в своём юните, даже если силлабус сменился.

`checkGrade`: `verdict` не `'checked'`/`'returned'` — `verdict/bad_value`; `checked` — `points` целое 0…`maxPoints`, иначе `points/bad_value`; `returned` — `points` не `null`/нет — `points/bad_value`, комментарий пуст после обрезки — `comment/empty`; `comment` не строка (и не нет) или длиннее 2000 — `comment/too_long`.

`selfByWork` — по таблице раздела «Правила расчёта»: `value = max > 0 ? Math.round(earned * self / max) : null`.

`taskCounts`: `fresh` — `none` и срок не прошёл; `soon` — `none`, срок не прошёл и дата срока не позже завтрашней по Бишкеку; `overdue` — `none` и срок прошёл; `returned` — `returned`.
