# Журнал колледжа

Электронный журнал для колледжа: Google Таблица как база, Google Apps Script как сервер, сайт на GitHub Pages. Пилот: 3 группы, 40 преподавателей. С владельцем говорим по-русски, простыми словами; он не программист и принимает работу по экранам и скриншотам.

## С чего начинать сессию

1. Прочитай `aidlc-docs/aidlc-state.md`: там, что сделано, что в работе, **следующие шаги по порядку** и таблица решений владельца. Выполняй шаги с первого незакрытого.
2. Сверься с `git log --oneline`: задача, коммит которой уже есть в истории, заново не запускается.
3. Журнал хода работ: у каждого плана свой рабочий каталог в `.superpowers/sdd/` (в git не попадает). Юнит 1 — `.superpowers/sdd/plan/progress.md`, юнит 2 — `.superpowers/sdd/plan-unit-2-raspisanie/progress.md`. Копии журналов лежат в `aidlc-docs/construction/<юнит>/sdd/ledger-snapshot.md`; после каждого этапа копию обновляй.

Документы:

- Требования: `aidlc-docs/inception/ТЗ.md`
- Дизайн версии 1: `aidlc-docs/inception/design-v1.md` (расписание, дисциплины, силлабус и семестры в нём описаны по-старому или не описаны: действуют таблица решений в `aidlc-state.md` и план юнита 2 с двумя дополнениями)
- План юнита: `aidlc-docs/construction/<юнит>/plan.md`; страница для владельца простыми словами: `owner-summary.md` рядом
- Старые номера коммитов (до 20.11.2026) → новые: `aidlc-docs/commit-map.md`

## Порядок работы (AI-DLC)

1. Версия 1 разбита на 6 юнитов, они идут по порядку.
2. На каждый юнит: план → согласие владельца → агенты пишут код и тесты → проверяющий после каждой задачи → общая проверка юнита → показ на локальном стенде → приёмка владельца → выкладка.
3. Агенты лежат в `.claude/agents/`: `journal-logic` (core/), `journal-server` (backend/, dev/, scripts/), `journal-screens` (site/), `journal-reviewer` (только отчёт). Основная сессия — координатор: раздаёт задачи, принимает работу, сама код не правит. Два агента не правят одни и те же файлы одновременно, задачи идут по одной.
4. Сборка ведётся по навыку `superpowers:subagent-driven-development`. Агенту дают короткое поручение и пути к файлам: памятка (`implementer-contract.md`, `reviewer-contract.md`, `rereview-contract.md` в рабочем каталоге плана; для нового плана их копируют и подставляют Global Constraints нового плана), задание задачи (скрипт навыка `task-brief`), отчёт. Каждое решение координатора записывается в журнал хода работ строкой `Ruling:`.
5. Модели: «Логика», «Сервер» и проверяющий — sonnet; «Экраны» — opus; планы юнитов, предварительная сверка большого плана и общая проверка юнита — самая сильная модель (fable). Модель всегда указывается явно.
6. После каждого шага обновляй `aidlc-docs/aidlc-state.md`.
7. Решение, которое меняет то, что увидит пользователь, или устройство базы, сначала согласуй с владельцем и запиши в таблицу решений в `aidlc-state.md`. Экраны показывай скриншотами до приёмки. Если новое решение отменяет старое, старое в таблице зачёркивается с пометкой «отменено».

### Что оправдало себя (делать так же)

- **Перед сборкой — сверка плана.** Проверяющий сверяет задачи между собой и с уже готовым кодом (имена, поля, существующие тесты, которые сломаются). Находки правит отдельный агент в самом `plan.md`, только потом первая задача. Для дополнений к плану — так же.
- **Мелкие замечания проверки** не возвращают агенту, а пишутся в журнал строкой `minor (deferred)` или передаются в следующую задачу того же агента. Важные — круг исправлений тому же агенту и короткая повторная проверка только этих правок.
- **Общая проверка юнита** — с пробными скриптами против настоящего кода; её находки исправляет **один** агент одной волной, затем короткая повторная проверка. Проверяющие часто не могут писать файлы отчёта — тогда находки координатор сам сохраняет в `.superpowers/sdd/<план>/…-fix-brief.md`.
- **Права и безопасность** проверять попыткой обойти защиту (чужой предмет, массив или пробелы вместо id и т. п.): так нашлась дыра в задаче 18.
- **Скорость на Google** — только настоящими тестами: шпион считает и `list`, и `get` по каждому листу.
- Агенту, который правит сайт, давать проверку на стенде со скриншотами в `.superpowers/sdd/<план>/task-N-shots/`; координатор сам смотрит 1–2 скриншота перед приёмкой задачи.
- Агенты коммитят **только свои файлы по имени** (не `git add -A`) и оставляют `git status` чистым: бывали изменения только в концах строк (CRLF) — их координатор откатывает, только убедившись, что `git diff` пустой.
- Перед экранными задачами стенд координатора на 5273 должен быть остановлен: агенты поднимают свой.
- **Браузер для проверки экранов агентами — только headless Chrome** с временным профилем и ключами `--disable-sync --disable-extensions`. **Не Edge:** 22.11.2026 новый профиль Edge сам вошёл в учётную запись Windows владельца и подтянул его вкладки и расширения. Браузер и учётные записи владельца агенты не трогают.
- **Исправления после общей проверки тоже проверять.** В доработке 2 повторная проверка дважды нашла новую ошибку в самой правке (силлабус на два семестра портил часы; тема «Жалпы анатомия» считалась строкой «Итого»). Круг исправлений отдаётся тому же агенту (продолжить его через SendMessage), повторную проверку делает тот же проверяющий. Совсем маленький круг координатор принимает сам: читает diff, запускает `npm test`, `npm run build:gas` и пробные скрипты проверяющего.
- **Правила про слова в файлах** (итого, семестр, вид занятия, часы) проверять и на кыргызских названиях: «жалпы» значит «общий», с него начинаются названия тем. Тема, которую журнал молча пропустил, сдвигает все следующие пары — лучше громкая ошибка, чем тихий пропуск.
- Проверяющий оставляет пробные скрипты во временной папке сессии; их путь передаётся исполнителю вместе с поручением — так ошибка воспроизводится без пересказа.
- Пока агент работает, координатор файлы репозитория не правит и не коммитит: агент видит чужие изменения в `git status`. Записи (`aidlc-state.md`, `CLAUDE.md`, копия журнала) коммитятся после агента, отдельным коммитом `docs:`.
- Пути Windows с обратной косой чертой в документы вставлять инструментом правки, а не через heredoc в Bash: там черта теряется.
- Владелец отвечает голосом и иногда пишет фразу для нового чата прямо в этот: тогда продолжаем здесь. Вопросы с вариантами задавать через окно вопросов; владелец любит «по умолчанию» с понятным вариантом.

## Команды

- `npm test` — все тесты
- `npm run dev` — локальный стенд на `http://localhost:5273` (данные вымышленные, пароль стенда в `dev/seed.js`)
- `npm run dev:reset` — стенд с чистыми данными
- `npm run dev:real` — стенд с **настоящими** данными владельца: тот же порт 5273, свой файл `dev/data/real.json` (в git не попадает), вымышленными людьми не заполняется, сброс в этом режиме запрещён. Агенты при проверке задач этот файл не трогают: они работают на `dev` и `dev:reset`
- `npm run build:gas` — сборка сервера для Apps Script в `build/gas/`
- `node scripts/vendor.js` — копирует библиотеку Excel и шрифты в `site/vendor/`
- В окне браузера приложения стенд поднимается по имени из `.claude/launch.json`: `journal-dev`, `journal-dev-reset` (с чистыми данными) или `journal-dev-real` (настоящие данные).
- **Вход на стенде** (вымышленные люди): `admin` — администратор, `dean` — деканат, `teacher1` — преподаватель, `S1001` — студент, `S1002` — студент со сменой временного пароля. Пароль один на всех: `journal2026` (он же в `dev/seed.js`, строка `DEV_PASSWORD`; если там изменится — поправить и здесь). Это пароль только локального стенда, поэтому по решению владельца он записан здесь. На стенде с настоящими данными (`journal-dev-real`) с ним входит один `admin`; остальным людям пароли выдаёт сам журнал. На живом сайте этого пароля нет. В чат его не пишут: владельцу называют это место или координатор сам входит за него в окне браузера приложения. У сотрудника с двумя ролями переключатель роли — слева внизу.
- Для приёмки координатор сам поднимает `journal-dev-reset`, входит как `dean` и даёт владельцу нумерованный список «что посмотреть»; после приёмки или перед экранными задачами агентов стенд останавливает.

## Выкладка (только по прямой просьбе владельца)

- Сайт: https://janybek.github.io/college-journal/ — репозиторий `janybek/college-journal` (открытый), GitHub Pages из GitHub Actions (`.github/workflows/pages.yml`), обновляется сам после `git push` в `main`.
- Сервер: Apps Script в Google-аккаунте колледжа. ID проекта и ID публикации записаны в `aidlc-state.md`, раздел «Выкладка». Обновление: `npm run build:gas` → `npx -y @google/clasp@latest push --force` → `npx -y @google/clasp@latest deploy -i <ID публикации> -d "<что изменилось>"`. Новую публикацию не создавать: сменится адрес.
- Если менялись листы или колонки (`core/schema.js`), порядок такой: `build:gas` → `clasp push --force` → владелец один раз запускает `setup` в редакторе Apps Script (дописывает новые листы и колонки, ничего не стирая) → `clasp deploy -i <ID публикации>` → **сразу** `git push`, чтобы сайт и сервер были одной версии (старый сайт на новом сервере не сохранит предмет). Так выкладывается юнит 2: в нём новые листы «Дисциплины», «Силлабусы» и новые колонки.
- Перед первой выкладкой нового кода на живой сервер — проверить вход и замерить время (пустой запрос к Google ≈ 2–3 с — это задержка самого Google).
- Пароль хэшируется 100 повторами (свой) и 20 (временный) — решение владельца «ускорить вход» от 21.11.2026.
- Коммиты подписываются скрытым адресом `janybek@users.noreply.github.com` (уже стоит в `user.email` репозитория); личную почту владельца в репозиторий не писать.

## Как устроен код

- `core/` — правила и расчёты, чистый JavaScript без Google, файлов и сети. Время и случайность приходят через объект `platform`.
- `backend/` — обработчики запросов и хранилища (память, файл, Google Таблица). `handleRequest` никогда не бросает исключений.
- `backend/gas/`, `backend/platform/gasPlatform.js` — единственное место, где используются объекты Apps Script.
- `site/` — сайт без сборки и фреймворков. Любая фраза идёт через словари `site/js/i18n/ru.js`, `ky.js`, `en.js` с одинаковыми ключами.
- `dev/` — локальный стенд: тот же сервер, данные в файле `dev/data/db.json`.
- `tests/` — тесты на `node --test`.

## Внешний вид (решения владельца)

- Образец — админ-панель Nexus UI: тёмно-синий фон, ярко-синий акцент, шрифт Inter, боковое меню у сотрудников, таблицы с метками статусов.
- Две темы с переключателем, тёмная по умолчанию. Будущий экран с QR для проектора — светлый.
- Студенческие экраны рассчитаны на телефон: без бокового меню, текст не мельче 16 px, кнопки не ниже 44 px.
- Цвета и размеры заданы переменными в `site/css/app.css`; новые экраны берут их оттуда.
- Код, стили, картинки и логотип шаблона не копируются: он платный. Повторяем вид своим кодом.

## Главные правила предметной области (решения владельца; полностью — в таблице решений `aidlc-state.md`)

- Подгрупп нет: у пары вся группа. Расписание одинаковое каждую неделю, шаблон пн–пт; отдельную пару можно перенести на субботу. Общих лекций нет: преподаватель, группа и аудитория не бывают на двух парах сразу.
- Звонки по умолчанию 08:00, 09:40, 11:20, 13:30, 15:10, 16:50, пара 90 минут; время выбирается из списка 07:00–22:25 с шагом 5 минут.
- Расписание меняют только деканат и администратор; проректор только смотрит.
- **Дисциплины и предметы:** название дисциплины вводится один раз в справочнике «Дисциплины»; предмет — это дисциплина + группа + преподаватель, его добавляют на экране «Предметы» одним окном (дисциплина из списка, группы и кто ведёт в каждой). При смене преподавателя у группы его будущие запланированные пары переходят новому (кроме тех, где новый занят), проведённые пары и разовые замены не меняются.
- **Силлабус — свой у каждого преподавателя по дисциплине** (и по половине года): действует во всех группах, где он её ведёт. Загружает **деканат** файлом Excel по шаблону журнала из двух листов — «Сведения» и «Тематический план»; преподаватель и студенты только смотрят. Строки плана идут в порядке пар; **1 пара = 2 часа**, в часах только 2 или 4; раздел курса — «Юнит» (может иметь название), контроль в его конце — «Модуль (рубежный контроль)». Семестр пишется как в учебном плане (1–8): нечётный — первая половина года, чётный — вторая; на пары встают темы текущей половины (переключатель в «Настройках семестра»). Исправления — только через файл: скачать, поправить, загрузить; загрузка «всё или ничего», темы проведённых пар защищены. Экрана «Темы» и правки тем по одной больше нет.
- Пока пары не отмечаются проведёнными (до юнита 3), семестр переключают одним сохранением вместе с новыми датами.
- Настоящие списки студентов на **живой сайт** загружаем только после юнита 3 (ограничение попыток входа). На локальный стенд с настоящими данными (`npm run dev:real`) — сразу, как владелец получит их от секретаря: в выдуманных именах он путается.
- Есть зачётная неделя и государственные экзамены (по каким предметам и у каких групп — в данных от секретаря). В юнитах 1–2 их нет; при плане юнитов 3–6 спросить владельца, что журнал должен с ними делать: только показывать в расписании или вести ведомость.
- Кыргызские тексты ждут вычитки носителем языка; спорное слово «сабак» сейчас значит и «пара», и «предмет».

## Настоящие данные колледжа (в репозитории их нет)

- Список того, что владелец просит у секретаря: `aidlc-docs/данные-для-секретаря.md` (там же — что уточнить у преподавателей); файл для отправки секретарю — `aidlc-docs/Данные для журнала.docx`. Это пустые формы с выдуманными примерами.
- Настоящие силлабусы: 13 PDF в папке `C:\Users\user\Desktop\Силабусы предметов`; 10 из них переведены в шаблон журнала и лежат в подпапке `Для журнала` вместе с `Отчёт о переводе.md`. Три не переведены: в них нет тематического плана или тем — нужен полный силлабус от преподавателя. Порядок пар в части файлов выбран при переводе, его подтверждает преподаватель.
- Когда придут данные секретаря: завести на стенде `journal-dev-real` группы, сотрудников, дисциплины и предметы, затем загрузить эти 10 файлов со строки «дисциплина + преподаватель». Файл стенда `dev/data/real.json` в git не попадает; агенты его не трогают и не сбрасывают.
- В отчётах, журнале хода работ, тестах и скриншотах настоящих имён нет; названия дисциплин писать можно.

## Жёсткие правила

- Настоящие данные студентов и сотрудников в репозиторий не попадают никогда: репозиторий открытый.
- Пароли и ключи не пишутся в чат и не кладутся в код. В Google и GitHub владелец входит сам в браузере.
- `git push` и выкладка в Google — только по прямой просьбе владельца.
- Адрес опубликованного Apps Script не должен меняться: обновляй существующую публикацию, а не создавай новую.
- Сайт ничего не загружает с чужих адресов: ни CDN, ни внешних шрифтов. Библиотеки и шрифты лежат в `site/vendor/`.
- Данные с сервера, от пользователя и из загруженных файлов попадают на страницу только как текст (`textContent`, помощники из `site/js/ui.js`), никогда через `innerHTML`.
- Цвета пишутся в hex или rgb, без `oklch()`: у студентов старые телефоны.
- `passwordHash` никогда не уходит в ответ сервера.
- Локальный стенд — только на порту 5273: на 5173 на этом компьютере живёт другой проект владельца.
