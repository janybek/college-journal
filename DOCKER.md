# Журнал колледжа: запуск в контейнере

Для администратора кластера. Образ содержит сервер журнала (Node.js 24, база SQLite) и сайт: сайт отдаётся с `/`, запросы журнала идут на `/api`, проверка работы — `/health`.

## Образ

- `ghcr.io/janybek/college-journal:latest` и `ghcr.io/janybek/college-journal:<короткий хеш коммита>` (собирается сам после каждого изменения в `main`).
- Работает от пользователя `node` (uid 1000). Файлы программы только для чтения.
- Порт внутри контейнера: **5373**.
- Реплика строго **одна**: база SQLite, второй экземпляр на той же базе нельзя.

## Тома

| Путь | Что там | Требование |
|---|---|---|
| `/data` | база `journal.sqlite`, ключ `secret.key`, папка `files/` с файлами сданных работ студентов | постоянный том, его копируют |
| `/backup` | ежедневные копии базы (хранятся 30 дней), копия `secret.key` и `files/` | постоянный том, лучше на другом диске, чем `/data` |

Оба тома должны быть доступны на запись пользователю с uid 1000 (в Kubernetes: `securityContext.fsGroup: 1000` или `runAsUser: 1000`). Ключ `secret.key` нельзя терять: без него входы всех пользователей перестанут действовать, а с ключом из копии продолжат.

## Переменные

| Переменная | По умолчанию в образе | Значение |
|---|---|---|
| `JOURNAL_DATA_DIR` | `/data` | папка базы |
| `JOURNAL_BACKUP_DIR` | `/backup` | папка копий |
| `JOURNAL_HOST` | `0.0.0.0` | на каком адресе слушает сервер (IPv4, `::` или `::1`). Встроенный `HEALTHCHECK` обращается к `127.0.0.1`, поэтому оставьте `0.0.0.0` (или `::`) |
| `JOURNAL_PORT` | `5373` | порт (от 1024; 5173 и 5273 заняты стендом разработки) |
| `JOURNAL_ORIGINS` | `https://janybek.github.io` | адреса сайта через запятую, только `https://адрес[:порт]`, без пути и без `*` |
| `JOURNAL_SITE_DIR` | `/app/site` | папка сайта; пусто — сайт не отдаётся, остаются только `/api` и `/health` |
| `JOURNAL_AUTO_INIT` | `1` | `1` — база создаётся сама при первом запуске |
| `JOURNAL_ALERT_DIR` | не задана | куда класть файл-тревогу о незапуске; в контейнере не нужна, тревоги смотрите в журнале контейнера |

**Адрес сайта обязательно записать в `JOURNAL_ORIGINS`**, например `JOURNAL_ORIGINS=https://journal.example.edu`. Сайт, открытый с этого адреса, шлёт запросы на `/api` того же адреса, и сервер принимает запрос, только если его адрес есть в списке. Без этого вход не заработает (ответ `forbidden_origin`).

## Первый запуск

1. Запустите контейнер с пустыми томами. База и `secret.key` создаются сами; пароль администратора при этом нигде не показывается и не записывается.
2. Получите временный пароль администратора командой (он показывается один раз):

   ```
   docker exec -it <контейнер> node backend/node/server.js --admin-password
   ```

   или в Kubernetes:

   ```
   kubectl exec -it <под> -- node backend/node/server.js --admin-password
   ```

   Команду можно выполнять при работающем сервере. Вход: логин `admin` и этот пароль; при первом входе журнал потребует сменить пароль. Если пароль потерян, команду можно выполнить ещё раз: она задаёт новый временный пароль.
3. Запись в журнале контейнера «base created automatically» означает, что база создана.

Запускайте с `docker run --init …`: процесс сервера в контейнере имеет PID 1 (в Kubernetes тоже), и остановка в первые секунды после старта может ждать окончания льготного срока; это безвредно.

## Проверка работы

`GET /health` отвечает `{"ok":true,"data":"journal","version":"<хеш>"}`: `version` — короткий хеш коммита, он совпадает с тегом образа (`ghcr.io/janybek/college-journal:<хеш>`), так видно, какая версия выкатилась. В образе уже есть `HEALTHCHECK`. На Node 24 в журнале при старте может быть строка `ExperimentalWarning: SQLite is an experimental feature`: это нормально.

## Прокси, доступ из интернета

- Перед контейнером нужен HTTPS (прокси или ingress). Лимит размера запроса прокси — **не меньше 20 МБ**: студенты сдают файлы до 10 МБ, а файл идёт в запросе в закодированном виде.
- Сервер сам не ограничивает доступ по адресам; сам он учёта клиентов по IP не ведёт, ограничение неверных паролей считается по логину.

## Перенос данных с компьютера владельца

1. Остановить сервер на компьютере владельца и **остановить контейнер**. Первый автоматический запуск мог создать в `/data` свою пустую базу: удалить там всё (`journal.sqlite`, `journal.sqlite-wal`, `journal.sqlite-shm`, `secret.key`, папку `files/`).
2. Скопировать **всю папку данных целиком** (`journal.sqlite`, `secret.key`, папку `files/`) в том `/data` при **остановленном** контейнере.
3. Проверить, что владелец файлов — uid 1000 (`chown -R 1000:1000`), и запустить контейнер.
4. Файлы `journal.sqlite-wal` и `journal.sqlite-shm`, если они есть рядом с базой, копировать вместе с базой; лучше перед копированием дождаться штатной остановки сервера, тогда их нет.

## Обновление

После обновления у людей со старым паролем при следующем входе пароль сам переходит на новую форму хранения; на других их устройствах придётся один раз войти заново.

Заменить образ на новый тег и перезапустить единственную реплику. Сервер сам достраивает недостающие таблицы базы. Перед обновлением сделайте копию тома `/data`. Откат: прежний тег образа; при порче данных — восстановление копии из `/backup`.
